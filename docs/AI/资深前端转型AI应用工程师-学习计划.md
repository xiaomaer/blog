# 资深前端转型 AI 应用工程师：学习计划

> 更新日期：2026-11-03。
> 适用背景：10 年前端开发经验，会一点 Node.js，了解一点 Python。
> 推进方式：按成果里程碑学习。每周可投入时间尚未确定，不设置固定完成日期。

## 一、目标与使用方式

### 1.1 学习方向

目标是成为能独立交付 AI 产品功能的工程师：保留前端开发、交互设计和工程化经验，补齐服务端、模型集成、数据检索、效果评估和线上运行能力。

### 1.2 完成这份计划后应具备什么

- 能把一个业务需求拆成模型任务、确定性程序逻辑和人工操作。
- 能独立部署包含前端、Node.js 服务、数据库和模型调用的应用。
- 能处理结构化输出、知识检索、工具调用、权限与失败恢复。
- 能建立评测集，定位失败原因，并说明一次改动对质量、耗时和成本的影响。
- 能用演示、代码、实验报告和真实反馈验证学习成果，识别需要继续补齐的能力。

### 1.3 如何执行

1. 先做阶段 0 的能力诊断，用实际操作决定需要补多少基础。
2. 全程围绕同一个工单助手项目推进，控制功能数量。
3. 每个阶段按“学习要点 → 实作任务 → 验收 → 复盘”完成。
4. 验收通过后再扩展；遇到薄弱环节时延长当前阶段。
5. Python 小练习、技术复盘和能力盘点贯穿全程。

此前讨论的 12 周安排只作为内容顺序参考。完成日期根据实际投入和验收情况确定，按掌握程度推进。

## 三、技术主线与学习边界

### 3.1 建议采用的技术路线

以下是练习项目的建议组合；开始实现时记录选定版本和原因，避免学习中频繁更换框架。

| 层次 | 建议 | 学习重点 |
| --- | --- | --- |
| 前端 | 沿用自己最熟悉的框架 | 流式状态、取消、错误恢复、引用展示、操作预览 |
| 主服务 | Node.js + TypeScript，选一个熟悉或轻量的服务框架 | API、权限、异步任务、资源清理、运行时校验 |
| 数据库 | PostgreSQL | 表关系、约束、索引、事务、迁移和连接池 |
| 模型接入 | 先通过供应商 SDK 或 HTTP 理解一次完整调用 | 消息、响应、工具协议、错误、用量；随后可按需使用 AI SDK |
| 检索 | 先建立简单检索基线，再按需增加 pgvector | 数据质量、权限过滤、召回、排序和引用 |
| Python | 数据清洗、批量评估和结果分析脚本 | 虚拟环境、类型提示、文件处理、异常、有限并发 |
| 测试 | 使用熟悉的测试工具 | 确定性业务测试、少量真实模型集成验证、质量评估 |
| 部署与观测 | 单服务部署起步，保留数据库和任务记录 | 配置、日志、健康检查、重启恢复、成本记录 |

AI SDK 是面向 TypeScript 应用的工具包，可以帮助组织模型调用与界面集成。学习时仍应能解释调用协议和状态变化。参考 [AI SDK 官方文档](https://ai-sdk.dev/docs/introduction)。

pgvector 提供 PostgreSQL 内的向量相似度检索能力。引入它的目的，是在现有数据库基础上完成检索练习；索引和近似搜索等优化根据数据量及测量结果再决定。参考 [pgvector 官方仓库](https://github.com/pgvector/pgvector)。

### 3.2 后续按需学习的内容

- Python Web 服务：项目中出现适合独立 Python 服务的任务时补充。
- LangChain、LangGraph 等编排框架：先理解调用循环和任务状态，再选择一个深入学习。
- MCP：工具接入需要跨客户端复用时，学习其协议、权限与生命周期。
- 微调、本地推理、GPU 优化：实际评估结果表明有必要时再投入。
- 多 Agent、复杂记忆、分布式部署：单流程已出现可测量的能力或扩展瓶颈时再探索。

选择工作流还是 Agent，应根据任务是否需要模型动态决定下一步，以及增加复杂度带来的收益判断。参考 [Anthropic：构建有效的 Agent](https://www.anthropic.com/research/building-effective-agents)。文章中的具体工具可能变化，主要学习架构取舍。

## 四、贯穿项目：工单处理助手

### 4.1 产品目标

帮助处理工单的人理解问题、查阅文档、生成回复草稿，并在明确确认后执行受限的工单更新。

**最小闭环：** 打开工单 → 生成摘要和分类 → 检索相关知识 → 查看有引用的回复草稿 → 查看操作预览 → 确认后更新工单 → 查看执行结果。

先使用自建或公开可用的示例资料和模拟业务数据。开始接入实际业务数据前，确认其使用授权和访问范围。

### 4.2 功能范围

| 必做功能 | 为什么要做 | 可展示的证据 |
| --- | --- | --- |
| 工单列表、详情与基础权限 | 证明服务端与数据交付能力 | 两个测试用户的访问隔离演示 |
| 摘要、分类、回复草稿 | 证明模型接入与结构化输出能力 | 输入、Schema 校验结果和失败样例 |
| 知识导入、更新、删除与引用 | 证明检索链路能力 | 检索片段、版本、来源和问答评估 |
| 查询工具、更新草稿与确认执行 | 证明工具和业务系统集成能力 | 执行记录、权限检查、重复请求测试 |
| 评测、日志和部署说明 | 证明结果可验证、问题可定位 | 评估报告、运行记录、可复现启动步骤 |

第一版先支持 Markdown 或纯文本资料；复杂 PDF、OCR、多语言、语音、多 Agent 等功能作为后续可选扩展。

### 4.3 推荐的数据与模块边界

- 用户、组织或访问范围：表示谁能访问哪些业务数据。
- 工单：标题、内容、状态、负责人、更新时间，以及必要的版本信息。
- 文档与片段：来源、版本、访问范围、文本和检索所需表示。
- 任务与执行记录：任务状态、工具参数、操作结果、错误与幂等标识。
- 评估记录：案例版本、模型、提示词、检索配置、结果、耗时和成本。

前端负责展示与操作；服务端负责身份、权限和业务约束；模型提供生成结果和工具调用建议。业务更新是否发生，以数据库和工具执行结果为准。

这些是职责边界，不要求一开始拆成多个服务或为每个概念建立独立数据库表。

## 五、分阶段学习与验收

### 阶段 0：能力诊断与项目范围

**目标：** 明确自己的起点、需要补齐的能力和练习项目的范围。

**任务：**

1. 完成第二部分的能力盘点，至少实作一次 API、SQL 和权限诊断任务。
2. 对照已有项目，写下三项可直接证明的优势、三项优先补齐的能力。
3. 写一页项目说明，限定工单助手第一版的用户、流程和验收场景。

**产出：** 能力盘点表、一页项目范围说明。

**验收：** 能明确项目需要哪些能力，以及下一阶段最应该解决哪个短板。

### 阶段 1：补齐 Node.js 与数据库交付能力

**目标：** 独立运行一个具备数据与权限边界的服务。

**学习要点：**

- Node.js 运行时与浏览器的差异；事件循环、异步 I/O，以及 CPU 密集任务对请求处理的影响。
- HTTP 请求生命周期、状态码、分页、参数校验和一致的错误返回。
- SQL 查询、关联、索引、唯一约束、事务与数据库迁移。
- 身份认证与资源授权的区别；从服务端身份信息推导访问范围。
- 环境配置、数据库连接、日志、启动与优雅关闭。

关于阻塞与并发，阅读 [Node.js：不要阻塞事件循环](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)；数据库从 [PostgreSQL 官方教程](https://www.postgresql.org/docs/current/tutorial.html)开始，重点实践查询和事务。

**实作任务：**

1. 建立工单查询、创建和受限更新 API，先把业务规则写清楚。
2. 使用运行时校验处理请求体、分页参数和工单状态。
3. 准备两个不同访问范围的测试用户，覆盖列表、详情和更新接口。
4. 为一次关联更新使用事务；用失败注入验证不会出现部分写入。
5. 编写数据库初始化或迁移步骤、示例配置和启动说明。
6. 部署一个可访问的练习环境，确认重启后业务数据仍然存在。

**验收清单：**

- [ ] 无需手动修改数据库即可从干净环境初始化并启动。
- [ ] 非法参数得到明确错误，未知资源与无权限场景有一致处理。
- [ ] 用户 A 无法通过修改 ID 查询或更新用户 B 的工单。
- [ ] 关键更新失败时能回滚；日志能关联请求和错误。
- [ ] 能解释索引、事务和权限校验分别解决了什么问题。

**理解自检：** “前端页面隐藏了按钮，为什么服务端还要校验权限？”“数据库提交成功但客户端没收到响应，会发生什么？”

### 阶段 2：模型接入、结构化输出与首批评估

**目标：** 做出能验证结果、能处理失败的 AI 功能。

**学习要点：**

- Token、上下文窗口、消息角色、模型能力和输入输出预算。
- 明确任务要求、提供示例、区分可信指令与用户或文档内容。
- 结构化输出、JSON Schema 和运行时业务校验。
- 流式事件、首个可见输出时间、用户取消与服务端取消传播。
- 超时、限流、有限重试，以及重试可能增加的费用。

**实作任务：**

1. 服务端调用一个模型，实现工单摘要和分类。
2. 将分类约束为有限枚举，缺失信息保留为空或标为未知。
3. 实现回复草稿的流式展示，区分生成中、完成、取消和失败状态。
4. 处理输出截断、拒绝、结构校验失败、限流和模型不可用。
5. 为提示词建立简单版本记录，保存模型标识、请求耗时和用量。
6. 建立约 30 条初始案例，覆盖正常、缺失、歧义、超长和干扰输入；从开始就区分开发案例和保留验收案例。

**验收清单：**

- [ ] 模型凭据只存在服务端；外部输入和模型输出均经过必要校验。
- [ ] 字段结构正确时仍检查业务合法性，例如负责人是否真实存在。
- [ ] 用户取消后服务端尝试取消上游请求，界面不再接受过期结果；理解上游是否已停止及费用需以实际接口行为为准。
- [ ] 测试能稳定覆盖超时和错误；真实调用用于验证模型效果，不要求输出逐字一致。
- [ ] 能拿出首份基线结果，解释最常见的失败类型。

**产出：** 可演示的摘要和草稿功能、初始评测集、基线报告、至少两个失败案例。

### 阶段 3：知识库、检索与引用

**目标：** 让回答有可追踪依据，并能定位检索与生成各自的问题。

**学习要点：**

- 文档质量、标题与段落切分、片段元数据、版本与重复导入。
- Embedding、向量相似度、关键词检索、Top-K 与上下文预算。
- 基于有标注案例衡量检索覆盖；按需要比较混合检索或重排序。
- 权限过滤、删除传播和引用可访问性。

**实作任务：**

1. 准备一批可以人工检查的产品说明、FAQ 或技术文档。
2. 实现导入、更新和删除，保留文档 ID、版本、来源与访问范围。
3. 建立简单检索基线，再与向量检索方案在同一组问题上比较。
4. 记录进入模型上下文的片段，控制片段数量和总长度。
5. 展示可定位的引用；没有足够资料时提示补充信息或人工处理。
6. 添加跨文档、文档冲突、无答案、更新后答案变化和跨用户访问案例。

**验收清单：**

- [ ] 重复导入不生成重复资料；删除或更新后不再使用失效片段。
- [ ] 未授权片段不会进入模型上下文；缓存和引用打开也遵守访问权限。
- [ ] 能分别查看检索命中情况、回答是否有依据，以及引用是否支持相关表述。
- [ ] 能区分“未检索到”“切分破坏上下文”“资料冲突”“生成错误”等原因。
- [ ] 至少完成一次有记录的切分或检索对比实验，每次尽量只改变一个因素。

**产出：** 知识问答演示、检索案例集、一次检索改进报告。

### 阶段 4：工具调用、工作流与任务恢复

**目标：** 将模型建议接入业务操作，确保操作结果可检查。

**学习要点：**

- 工具描述、输入 Schema、执行结果和错误语义。
- 完整调用过程：模型提出调用 → 程序校验 → 执行 → 回传结果。
- 固定工作流与动态 Agent 的取舍；循环、时间和调用预算。
- 任务状态、持久化、幂等、并发修改和人工确认。

**实作任务：**

1. 实现搜索知识、查询工单、生成更新草稿三个小工具。
2. 写操作先生成预览，用户确认后由服务端执行；模型无法自行授予确认。
3. 确认绑定具体操作、参数和目标版本，执行前重新校验身份、权限与当前状态。
4. 保存任务和执行记录，区分等待确认、执行中、完成、失败与取消。
5. 使用数据库唯一约束或等效机制处理幂等请求，避免仅靠前端禁用按钮。
6. 注入工具超时、非法参数、权限拒绝、执行后响应丢失和重复提交场景。
7. 为循环设置明确上限；如需动态决策，再增加一个可追踪的单 Agent 循环。

**验收清单：**

- [ ] 模型提出的调用不会绕过服务端权限与业务规则。
- [ ] 用户确认后的参数被修改时，需要重新确认；过期预览不能直接执行。
- [ ] 重复请求不会产生重复业务更新，恢复时能识别已完成的操作。
- [ ] 外部系统结果不确定时，先查询结果或交由人工确认，不盲目重放写操作。
- [ ] 工具失败和达到预算上限时，流程能够结束并显示真实状态。
- [ ] 能从执行记录还原任务过程，无需依赖模型声称“已完成”。

**产出：** 确认式业务操作、状态与恢复说明、关键异常测试记录。

### 阶段 5：质量、性能、成本与交付

**目标：** 证明功能可持续改进，并能在运行中定位问题。

**学习要点：**

- 分层评估、保留验收集、人工评分与自动评分的配合。
- 模型或提示词变化带来的回归、波动与版本追踪。
- 首个输出时间、总耗时、并发限制和单任务成本。
- 日志脱敏、配置管理、服务重启、任务恢复和反馈收集。

**实作任务：**

1. 随着功能增加，把评测集扩展至约 80～100 条或足以覆盖主要场景的规模；保留样例来源和版本。
2. 将确定性测试与模型质量评估分开，建立人工核对的评分规则。
3. 对一次提示词、模型或检索改动执行对比实验，记录质量、耗时、费用和退步案例。
4. 在受控条件下测试少量并发请求，明确请求数量、输入长度和模型配置。
5. 对典型随机性场景多次运行，报告波动；低样本性能分位数标注样本量和限制。
6. 检查重启后的数据、任务状态和错误恢复，整理部署与排障说明。
7. 邀请少量用户完成具体任务，记录其操作和反馈；没有真实用户时明确标为个人试用。

**验收清单：**

- [ ] 提供可重复运行的评估入口及配置说明。
- [ ] 报告能追溯到案例、提示词、模型和知识库版本。
- [ ] 评估只承诺已覆盖的场景，未把有限样本结论当作生产可靠性保证。
- [ ] 有日志、耗时和成本证据支持一次改进，能够解释取舍。
- [ ] 从干净环境能够重新部署，凭据和业务敏感内容不会被公开提交或直接记录。

**产出：** 综合评估报告、运行与排障说明、试用反馈、一次完整项目演示。

## 六、评估与验证的具体做法

### 6.1 区分三类验证

| 类型 | 检查对象 | 典型例子 |
| --- | --- | --- |
| 确定性自动化测试 | 程序与业务规则 | 越权拒绝、参数校验、幂等、状态转换、事务回滚 |
| 模型质量评估 | 具有变化性的输出和任务结果 | 摘要覆盖、分类、依据、引用、工具选择与任务完成 |
| 用户试用 | 实际任务中的可用性 | 是否读懂结果、是否能纠正错误、是否节省处理时间 |

为评测案例定义输入、预期行为和评分依据；复杂任务还应检查最终系统状态。必要时多次尝试同一任务，以识别运行波动。参考 [Anthropic：Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

### 6.2 每条案例建议记录的字段

| 字段 | 内容 |
| --- | --- |
| 案例 ID、来源、版本 | 自建、脱敏历史问题或用户反馈；避免重复案例污染比较 |
| 输入与初始状态 | 用户问题、工单状态、身份、可用文档 |
| 预期行为 | 应回答、应追问、应拒绝或应执行的操作 |
| 评分依据 | 参考事实、允许的结果、必要引用、工具执行约束 |
| 案例用途 | 开发调参或保留验收；验收集被反复用于修改后需补充新保留集 |
| 实际结果 | 输出、工具记录、最终业务状态及错误分类 |
| 运行配置 | 模型、提示词版本、知识版本、检索设置 |
| 耗时与成本 | 可见输出时间、总耗时、用量、重试和工具费用 |

### 6.3 指标应明确分母与适用范围

- 结构有效率：通过 Schema 校验的输出数 / 需要结构化输出的有效请求数；另行统计超时等请求失败。
- 分类效果：按类别查看错误，避免总准确率掩盖少数类别问题。
- 检索覆盖：在标注了相关资料的问题上，衡量 Top-K 结果对相关资料的覆盖情况。
- 引用支持率：被正确证据支持的受检表述 / 需要证据支持的受检表述，并检查来源是否可访问。
- 任务成功率：满足预先定义的最终结果条件的任务数 / 纳入评估的任务数。
- 单次成功任务成本：这一批任务的全部计量成本 / 成功任务数，包含失败和重试费用；成功数为零时标记不可计算。
- 延迟：分别记录首个可见输出和任务结束时间，区分成功、失败及取消请求。

先形成基线，再根据业务目标设定质量、耗时和成本门槛，并在实验前记录。权限绕过、未经确认的写操作和重复业务执行应作为阻止交付的问题处理。

## 2. A Concept Map for Frontend Developers

### 2.1 Concept Comparisons and Reading Order

| JS / TS experience | Python counterpart | What changes during the transition |
| --- | --- | --- |
| `constructor` | `__init__` | `__init__` initializes an existing instance; `__new__` primarily handles creation. |
| `toString()` | `__str__` / `__repr__` | User-facing display and debugging have separate entry points. |
| Functions and closures | Functions, closures, and objects implementing `__call__` | Objects can be called directly as `obj(...)`. |
| Property interception with `Proxy` | `__getattr__` / `__getattribute__` | Their trigger conditions differ; neither is a complete equivalent of JS `Proxy`. |
| Higher-order functions and wrappers | Decorators | Decoration happens at definition time; later calls use the decorated object. |
| `Symbol.iterator`, `next()` | `__iter__`, `__next__` | Python uses `StopIteration` to signal the end of iteration. |
| `function*`, `yield` | A `def` containing `yield` | Generators suspend and retain state; they are usually consumed once. |
| `async function`, Promise | `async def`, coroutine objects, Tasks | Calling a coroutine function normally creates an object without immediately executing its body. |
| `Promise.all()` | `gather()` / `TaskGroup` | Result handling, exception propagation, and sibling cancellation are not identical. |
| Web Workers / Node Workers | Threads or processes | The useful analogy is delegating work; memory and communication models require separate study. |

Recommended order: **object protocols → function wrappers → lazy data flow → concurrency and resource management**. First learn to read and write correct code; metaclasses and custom event loops can come later.

### 2.2 Scope and Closures: When Variables Are Read

Python names bind to objects. Reassigning a name and mutating its object are different operations. LEGB is a useful starting point for common lookup: local, enclosing function, module-global, and built-in names. Class bodies and comprehensions have additional rules; LEGB is not a complete account of every case.

Ordinary `if`, `for`, and `while` statements do not introduce a new local scope. An assignment to a name anywhere in a function normally makes it local, even when the assignment is inside a branch that has not executed. Use `nonlocal` explicitly to rebind a variable in an enclosing function. [Name binding and resolution](https://docs.python.org/3.14/reference/executionmodel.html#resolution-of-names)

```python
from collections.abc import Callable


def make_counter() -> Callable[[], int]:
    count = 0

    def increment() -> int:
        nonlocal count
        count += 1
        return count

    return increment


first = make_counter()
second = make_counter()
assert first() == 1
assert first() == 2
assert second() == 1
```

`count += 1` reads the old value and binds a new integer to `count`, so it needs `nonlocal` here. Calling `items.append(...)` on an outer list changes the object rather than rebinding `items`, and normally does not require `nonlocal`.

Another common issue is **late binding in closures**: a function reads the captured variable when called, rather than automatically storing its value at creation time.

```python
from collections.abc import Callable


def make_handlers() -> list[Callable[[], int]]:
    handlers = []
    for index in range(3):
        handlers.append(lambda: index)
    return handlers


def make_fixed_handlers() -> list[Callable[[], int]]:
    handlers = []
    for index in range(3):
        handlers.append(lambda index=index: index)
    return handlers


assert [handler() for handler in make_handlers()] == [2, 2, 2]
assert [handler() for handler in make_fixed_handlers()] == [0, 1, 2]
```

Unlike this Python loop, JS `for (let i = ...)` creates a separate binding for each iteration. The corrected version uses a default argument to capture the current integer when the function is created; a factory function can also create a separate closure. Capturing a mutable object still captures a reference, not a deep copy. [Closure variables in loops](https://docs.python.org/3.14/faq/programming.html#why-do-lambdas-defined-in-a-loop-with-different-values-all-return-the-same-result)

### 2.3 Mutable Defaults and Shallow Copies: Where Sharing Comes From

Default argument expressions are evaluated when a function definition executes, not on every call. A list or dictionary used as a default can therefore share state across calls.

```python
def append_bad(value: int, bucket: list[int] = []) -> list[int]:
    bucket.append(value)
    return bucket


def append_good(value: int, bucket: list[int] | None = None) -> list[int]:
    if bucket is None:
        bucket = []
    bucket.append(value)
    return bucket


first = append_bad(1)
second = append_bad(2)
assert first is second
assert first == [1, 2]
assert append_good(1) == [1]
assert append_good(2) == [2]

provided: list[int] = []
assert append_good(3, provided) is provided
assert provided == [3]
```

Use `is None` here rather than replacing the code with `bucket = bucket or []`: an explicitly supplied empty list is a valid container and should not be silently replaced. `append_bad` deliberately demonstrates incorrect behavior and should not be copied into application code. [Shared default values](https://docs.python.org/3.14/faq/programming.html#why-are-default-values-shared-between-objects)

Assignment, shallow copying, and deep copying are also distinct:

```python
from copy import deepcopy

original = {"tags": ["python"]}
alias = original
shallow = original.copy()
deep = deepcopy(original)

assert alias is original
assert shallow is not original
assert shallow["tags"] is original["tags"]
shallow["tags"].append("asyncio")

assert original["tags"] == ["python", "asyncio"]
assert deep["tags"] == ["python"]
```

JS object spread has similar shallow-copy behavior: a new outer container does not imply new nested objects. `deepcopy()` recursively copies objects that support copying, but resources such as connections and files are not appropriate targets. Decide how much to copy from ownership requirements instead of using deep copies to hide unclear sharing. [copy documentation](https://docs.python.org/3.14/library/copy.html)

## 3. Special Methods: Participating in Language Protocols

### 3.1 Special Methods Follow Defined Protocols

Double-underscore methods are often called dunder methods. Python looks up these special methods according to defined rules when performing built-in operations.

| Usage | Relevant methods | Purpose |
| --- | --- | --- |
| `TaskBatch(...)` | `__new__`, `__init__` | Create and initialize an instance. |
| `print(batch)` / `str(batch)` | `__str__` | Concise user-facing representation. |
| `repr(batch)` | `__repr__` | Developer-facing debugging representation. |
| `len(batch)` | `__len__` | Container length. |
| `batch(prefix)` | `__call__` | Make the instance callable. |
| `for item in batch` | `__iter__` | Obtain an iterator. |
| `batch[index]` | `__getitem__` | Index or key access. |
| `obj.missing` | `__getattr__` | Fallback after ordinary attribute lookup fails. |
| `with resource as value` | `__enter__`, `__exit__` | Define entry and cleanup behavior. |
| `a == b` / `a + b` | `__eq__` / `__add__`, etc. | Define comparison and arithmetic semantics. |

These are protocol entry points; an advanced class does not need to implement all of them. Implicit special-method lookup normally uses the type, so define these methods on the class. Assigning `__len__` to a single instance does not necessarily change `len(obj)`. See the [Python data model](https://docs.python.org/3.14/reference/datamodel.html#special-method-names) for the contracts.

### 3.2 Supporting Display, Calls, and Iteration in One Object

```python
from collections.abc import Iterator


class TaskBatch:
    def __init__(self, names: list[str]) -> None:
        self._names = tuple(names)

    def __repr__(self) -> str:
        return f"TaskBatch(names={self._names!r})"

    def __str__(self) -> str:
        return f"Task batch: {len(self)} items"

    def __len__(self) -> int:
        return len(self._names)

    def __iter__(self) -> Iterator[str]:
        return iter(self._names)

    def __call__(self, prefix: str) -> list[str]:
        return [name for name in self if name.startswith(prefix)]


batch = TaskBatch(["build", "test", "typecheck"])
print(batch)
print(repr(batch))
assert len(batch) == 3
assert list(batch) == ["build", "test", "typecheck"]
assert batch("t") == ["test", "typecheck"]
assert list(batch) == list(batch)
```

Three design choices matter here:

1. Converting the input to a tuple prevents later changes to the original list from changing the batch.
2. `__iter__` returns a fresh iterator on each call, so the batch can be traversed repeatedly.
3. `__call__` provides filtering, but a normal method such as `batch.filter_by_prefix()` is equally appropriate when it reads more clearly.

`__repr__` should provide useful, unambiguous information; not every representation must be executable code that reconstructs the object. Representations used in logs should not expose access tokens, passwords, or other secrets.

### 3.3 Comparing `__getattr__` and `__getattribute__`

- `__getattribute__` participates in ordinary instance attribute reads; overriding it can easily cause recursion.
- `__getattr__` runs only after ordinary attribute access fails with `AttributeError`.
- Missing attributes should still raise `AttributeError`, or operations such as `hasattr()` can report incorrect results.

This restricted configuration view demonstrates the mechanism; it is not a general-purpose data model:

```python
class ConfigView:
    def __init__(self, values: dict[str, str]) -> None:
        self._values = values.copy()

    def __getattr__(self, name: str) -> str:
        try:
            return self._values[name]
        except KeyError as exc:
            raise AttributeError(name) from exc


config = ConfigView({"region": "local"})
assert config.region == "local"
assert not hasattr(config, "missing")
assert getattr(config, "missing", "fallback") == "fallback"
```

Existing attributes take priority, so keys that conflict with methods or internal fields may not be accessible through dot notation. Explicit attributes or a `dataclass` are usually clearer for fixed business structures. Do not sacrifice type information and readability just to avoid brackets.

### 3.4 Context Managers: Keep Cleanup with Resource Use

Frontend code often releases resources with `try/finally`. Python's `with` packages that lifecycle into a protocol: acquire on entry and clean up on exit, including exceptional exits.

```python
from types import TracebackType


class Session:
    def __init__(self) -> None:
        self.closed = True

    def __enter__(self) -> "Session":
        self.closed = False
        return self

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc_value: BaseException | None,
        traceback: TracebackType | None,
    ) -> None:
        self.closed = True


session = Session()
try:
    with session as active:
        assert active is session
        assert not active.closed
        raise ValueError("Simulated business failure")
except ValueError:
    pass
assert session.closed
```

`as active` receives the value returned by `__enter__`. A truthy return from `__exit__` suppresses an exception from the block; this example returns `None`, so the exception propagates. The `with` statement arranges an exit call only after `__enter__` succeeds. Entry code must handle cleanup for partially initialized resources if entry itself fails.

Files, connections, and locks need explicit lifetimes rather than reliance on `__del__` or eventual garbage collection. Async resources use `async with`, `__aenter__`, and `__aexit__`.

### 3.5 Boundaries for Operator Overloading and Metaprogramming

Knowing that `__add__` customizes `+` does not mean every business object should overload operators. Use overloading when the meaning is natural and predictable.

Value equality also requires a hashing contract: equal objects must have equal hashes. State used to hash a dictionary key or set element must remain stable. An operation that does not support the other operand usually returns `NotImplemented` so the interpreter can try further dispatch; this differs from raising `NotImplementedError`.

The following sections cover method binding, `property`, and basic descriptors. Deep metaclass customization can wait; the goal is to understand common object behavior and justify each method you implement.

### 3.6 Method Binding: `self`, Class Attributes, and Three Method Types

The first parameter of a Python instance method is conventionally named `self`. Looking up an ordinary method on an instance produces a bound method that retains that instance, even when passed elsewhere as a callback. This differs from ordinary JS functions whose `this` depends on how they are called.

| Method form | Automatically supplied argument | Typical purpose |
| --- | --- | --- |
| Instance method | The instance, `self` | Read or modify one object's state. |
| `@classmethod` | The class, `cls` | Alternative constructors and operations that should respect subclasses. |
| `@staticmethod` | No implicit instance or class | A related helper that does not depend on instance or class state. |

```python
class User:
    def __init__(self, name: str) -> None:
        self.name = name

    def greet(self) -> str:
        return f"Hello, {self.name}"

    @staticmethod
    def normalize(name: str) -> str:
        return name.strip().lower()

    @classmethod
    def from_text(cls, text: str) -> "User":
        return cls(cls.normalize(text))


class Admin(User):
    pass


user = User.from_text(" Mia ")
callback = user.greet
assert callback.__self__ is user
assert callback() == "Hello, mia"
assert User.greet(user) == callback()
assert isinstance(Admin.from_text(" Root "), Admin)
```

The factory calls `cls(...)`, allowing a subclass to construct its own instances. If a helper does not conceptually belong to a class, a module-level function is sufficient; do not force it into a `staticmethod` just for organization. [Functions and method binding](https://docs.python.org/3.14/howto/descriptor.html#functions-and-methods)

Class attributes can also introduce shared state. First observe the mistake, then give each instance its own list:

```python
class SharedLabels:
    labels: list[str] = []


left = SharedLabels()
right = SharedLabels()
left.labels.append("python")
assert right.labels == ["python"]
assert left.labels is right.labels


class OwnLabels:
    def __init__(self) -> None:
        self.labels: list[str] = []


first = OwnLabels()
second = OwnLabels()
first.labels.append("python")
assert second.labels == []
```

`left.labels.append()` mutates the list found on the class; it does not create a new list for `left`. Assigning `left.labels = [...]` is a different operation. Fixed configuration can live on the class; mutable per-instance data should be created during instance initialization.

### 3.7 `property` and Descriptors: Attribute Access Can Execute Logic

Like familiar frontend getters and setters, `property` can attach validation or computation to a clear attribute interface.

```python
class WorkerConfig:
    def __init__(self, workers: int) -> None:
        self.workers = workers

    @property
    def workers(self) -> int:
        return self._workers

    @workers.setter
    def workers(self, value: int) -> None:
        if value <= 0:
            raise ValueError("The worker count must be positive")
        self._workers = value


config = WorkerConfig(3)
assert config.workers == 3
try:
    config.workers = 0
except ValueError:
    pass
else:
    raise AssertionError("An invalid count must be rejected")
assert config.workers == 3
```

The type hints here specify that callers supply integers; they do not automatically validate arbitrary external input. Hiding network calls or expensive queries behind ordinary property reads can also obscure costs, so design the API around predictable behavior.

When the same attribute rule needs to be reused across fields or classes, descriptors provide a deeper mechanism. They are normally stored as class attributes and participate in access through methods such as `__get__` and `__set__`:

```python
class Positive:
    def __set_name__(self, owner: type, name: str) -> None:
        self.storage_name = f"_{name}"

    def __get__(self, instance: object | None, owner: type | None = None):
        if instance is None:
            return self
        return getattr(instance, self.storage_name)

    def __set__(self, instance: object, value: int) -> None:
        if value <= 0:
            raise ValueError("The value must be positive")
        setattr(instance, self.storage_name, value)


class Limits:
    workers = Positive()
    capacity = Positive()

    def __init__(self, workers: int, capacity: int) -> None:
        self.workers = workers
        self.capacity = capacity


first = Limits(3, 6)
second = Limits(1, 2)
assert first.workers == 3
assert first.capacity == 6
assert second.workers == 1
assert isinstance(Limits.workers, Positive)
```

The descriptor stores the field rule and storage name; each business instance stores its own value. Storing the value directly on `Positive` would risk sharing it across all `Limits` instances.

A useful simplified order for ordinary instance lookup is **data descriptor → instance attribute dictionary → non-data descriptor or other class attribute → `__getattr__` after failure**. Inheritance order also affects class lookup, and overriding `__getattribute__` can change behavior. A descriptor defining `__set__` or `__delete__` is a data descriptor; method binding by ordinary functions is a common use of non-data descriptors. [Descriptor lookup rules](https://docs.python.org/3.14/howto/descriptor.html#invocation-from-an-instance)

### 3.8 `dataclass`: Design Fields, Equality, and Hashing Together

`dataclass` generates common methods from field definitions, reducing repetitive `__init__`, `__repr__`, and `__eq__` code. It is neither a runtime data validator nor a direct equivalent of a TS `interface`.

```python
from dataclasses import FrozenInstanceError, dataclass, field


@dataclass
class User:
    name: str
    tags: list[str] = field(default_factory=list)


first = User("Mia")
second = User("Mia")
assert first == second
assert first is not second
assert first.tags is not second.tags
first.tags.append("python")
assert first != second
assert User.__hash__ is None


@dataclass(frozen=True)
class CacheKey:
    tenant: str
    tags: tuple[str, ...]


key = CacheKey("team-a", ("python",))
same_key = CacheKey("team-a", ("python",))
assert key == same_key
assert hash(key) == hash(same_key)
assert len({key, same_key}) == 1


@dataclass(frozen=True)
class FrozenLabels:
    tags: list[str] = field(default_factory=list)


labels = FrozenLabels()
labels.tags.append("still mutable")
assert labels.tags == ["still mutable"]
try:
    labels.tags = []
except FrozenInstanceError:
    pass
else:
    raise AssertionError("Frozen fields must reject reassignment")

try:
    hash(labels)
except TypeError:
    pass
else:
    raise AssertionError("A list field participating in hashing is unhashable")
```

Remember four points from this example:

1. `default_factory=list` creates a list when a default is needed, preventing instances from sharing one mutable default.
2. Generated equality compares fields and requires matching types; equal values do not imply identical objects.
3. A default `eq=True, frozen=False` data class is unhashable. `eq=True, frozen=True` normally generates a hash method, but every participating field must also be hashable.
4. `frozen=True` restricts field reassignment without recursively freezing referenced objects. It is not deep immutability, and it differs from TS `readonly`, which is enforced by static checking.

Do not use `unsafe_hash=True` to hide a mutable-key design problem. Prefer explicitly immutable fields for stable cache keys. [Data class parameters and field rules](https://docs.python.org/3.14/library/dataclasses.html)

## 4. Decorators: Composing Behavior and Preserving Contracts

### 4.1 Expand `@` Back into a Function Call

The most useful equivalence to remember is:

```text
@decorate
def handle(...): ...

Equivalent to:
def handle(...): ...
handle = decorate(handle)
```

A decorator accepts the decorated object and returns its replacement. A typical function decorator returns a wrapper, but it may also register and return the original function. Creating a new function is not mandatory.

The decorator is applied when execution reaches the function definition, often during module import. Registering a route at definition time differs from checking authorization on every request. [Function definitions and decorator semantics](https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions)

### 4.2 Relating Python and TypeScript Decorators

The closest starting analogy is a JS higher-order function such as `withLogging(handler)`. TS decorators applied to classes or members have their own rules for arguments, context, and valid targets.

Decorator support introduced in TS 5.0 differs from the older `experimentalDecorators` mode. Do not transfer legacy decorator signatures or metadata assumptions from projects such as NestJS directly into Python. [TypeScript 5.0 decorators](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators)

### 4.3 A Configurable Synchronous Decorator That Preserves Types

This example implements `@timed("label")`. Its three function layers receive configuration, receive the original function, and handle each call, respectively.

```python
from collections.abc import Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def timed(label: str) -> Callable[[Callable[P, R]], Callable[P, R]]:
    def decorate(func: Callable[P, R]) -> Callable[P, R]:
        @wraps(func)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            started = perf_counter()
            try:
                return func(*args, **kwargs)
            finally:
                elapsed = perf_counter() - started
                print(f"{label}: {elapsed:.6f}s")

        return wrapper

    return decorate


@timed("Addition")
def add(left: int, right: int = 1) -> int:
    """Return the sum of two integers."""
    return left + right


assert add(2, right=3) == 5
assert add.__name__ == "add"
assert add.__doc__ == "Return the sum of two integers."
```

Each part has a distinct responsibility:

- `*args` and `**kwargs` forward arguments; `return` preserves the result.
- `try/finally` records time for successful and exceptional calls while allowing exceptions to propagate.
- `wraps` preserves metadata such as the name and docstring, and sets `__wrapped__` for introspection; it does not perform static type checking.
- `ParamSpec` describes the parameter list and `TypeVar` the result, allowing a type checker to understand the contract before and after wrapping.

Annotations do not themselves validate arguments at runtime. Distinguish static contracts from runtime metadata when reading about [ParamSpec](https://docs.python.org/3.14/library/typing.html#typing.ParamSpec) and [functools.wraps](https://docs.python.org/3.14/library/functools.html#functools.wraps).

### 4.4 The Order of Multiple Decorators

```text
@outer
@inner
def work(): ...

Equivalent to work = outer(inner(work))

If each wrapper runs setup, calls its wrapped function, and then runs cleanup:
outer setup → inner setup → work → inner cleanup → outer cleanup
```

Decorator expressions are evaluated from top to bottom and their results applied from the inside out. For configurable decorators, distinguish when the factory runs from when the wrapper runs.

Order affects behavior: a cache outside authorization may bypass the inner authorization check on a cache hit. A timer inside a cache measures only computations on misses. Write down the intended call sequence before choosing the order.

### 4.5 Standard Cache Decorators and Their Limits

```python
from functools import lru_cache


@lru_cache(maxsize=128)
def normalize_tag(tag: str) -> str:
    return tag.strip().lower()


assert normalize_tag(" Python ") == "python"
assert normalize_tag(" Python ") == "python"
assert normalize_tag.cache_info().hits == 1
normalize_tag.cache_clear()
assert normalize_tag.cache_info().currsize == 0
```

Before caching, answer these questions:

1. Are the arguments hashable? Lists and dictionaries normally cannot be used directly as cache keys.
2. Should identical arguments produce a reusable result? Current time, randomness, or mutable external state may make caching inappropriate.
3. Is the result mutable? A caller changing a cached list affects later readers.
4. Do you need expiration, cross-process sharing, or per-user isolation? `lru_cache` does not supply those business policies.

Do not apply `lru_cache` directly to `async def`: that caches coroutine objects rather than their awaited results. A completed native coroutine cannot be executed again. [Cache applicability](https://docs.python.org/3.14/library/functools.html#functools.lru_cache)

### 4.6 Async Functions Require Waiting for the Actual Work

A synchronous timing wrapper that merely calls an async function measures coroutine creation. The following wrapper awaits the original function, so its timing includes actual execution:

```python
import asyncio
from collections.abc import Awaitable, Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def async_timed(
    func: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(func)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            print(f"{func.__name__}: {perf_counter() - started:.4f}s")

    return wrapper


@async_timed
async def load_title() -> str:
    await asyncio.sleep(0.01)
    return "Python"


async def main() -> None:
    assert await load_title() == "Python"


if __name__ == "__main__":
    asyncio.run(main())
```

When you later implement retries, explicitly limit retryable exceptions, attempts, and backoff, and confirm the operation is idempotent. Use `asyncio.sleep()` for async delays. Do not catch every exception and retry indefinitely or swallow task cancellation.

## 5. Iterators and Generators: Processing Data on Demand

### 5.1 Keep Three Concepts Separate

| Concept | Meaning | Typical examples |
| --- | --- | --- |
| `Iterable` | Supports obtaining an iterator with `iter(obj)` | Lists, tuples, and this guide's `TaskBatch`. |
| `Iterator` | Tracks a consumption position and supports `next()` | `iter([1, 2, 3])` and file objects. |
| `Generator` | A specialized iterator from a generator function or expression | `(n * 2 for n in range(3))`. |

Every iterator is iterable, but not every iterable is an iterator. An iterator's `__iter__()` returns itself; `__next__()` raises `StopIteration` when exhausted. A `for` loop handles that completion signal. [Iterators and generators tutorial](https://docs.python.org/3.14/tutorial/classes.html#iterators)

```python
class Countdown:
    def __init__(self, start: int) -> None:
        self.current = start

    def __iter__(self) -> "Countdown":
        return self

    def __next__(self) -> int:
        if self.current <= 0:
            raise StopIteration
        value = self.current
        self.current -= 1
        return value


counter = Countdown(3)
assert iter(counter) is counter
assert next(counter) == 3
assert list(counter) == [2, 1]
assert list(counter) == []
```

The final line is intentional: the iterator is exhausted. Create another iterator to consume the sequence again; an arbitrary `Iterable` is not necessarily a reusable list.

### 5.2 Preserving Execution State with `yield`

```python
from collections.abc import Iterator


def countdown(start: int) -> Iterator[int]:
    while start > 0:
        yield start
        start -= 1


items = countdown(3)
assert next(items) == 3
assert next(items) == 2
assert next(items) == 1
assert next(items, "done") == "done"
```

Calling `countdown(3)` creates a generator object. Its body starts on the first `next()`. Reaching `yield` produces a value and suspends execution; the next request resumes from that point.

- `yield value`: suspend and produce a value while retaining local state.
- `return`: finish the generator without producing more values.
- `yield from other`: delegate iteration to another iterable and forward parts of generator-protocol interaction.
- `send()`, `throw()`, and `close()`: send values, inject exceptions, or close a generator. Prioritize ordinary iteration and closing in this stage.

End a generator with `return` rather than explicitly raising `StopIteration`. Also, `yield` does not imply asynchronous execution: a generator may perform blocking file reads. [Yield expressions](https://docs.python.org/3.14/reference/expressions.html#yield-expressions)

### 5.3 Streaming a JSON Lines File

Suppose each line contains a JSON object and we want to filter error records. Letting the caller own the file lifetime and the generator handle parsing avoids closing the file before consumption finishes.

```python
import json
from collections.abc import Iterable, Iterator
from pathlib import Path
from tempfile import TemporaryDirectory
from typing import Any


def parse_jsonl(lines: Iterable[str]) -> Iterator[dict[str, Any]]:
    for line_number, line in enumerate(lines, start=1):
        if not line.strip():
            continue
        record = json.loads(line)
        if not isinstance(record, dict):
            raise ValueError(f"Line {line_number} must contain a JSON object")
        yield record


with TemporaryDirectory() as directory:
    path = Path(directory) / "events.jsonl"
    path.write_text(
        '{"level": "info", "message": "started"}\n'
        '{"level": "error", "message": "failed"}\n',
        encoding="utf-8",
    )

    with path.open(encoding="utf-8") as source:
        errors = (
            row for row in parse_jsonl(source) if row.get("level") == "error"
        )
        first = next(errors)
        assert first["message"] == "failed"

    assert source.closed
```

Reading, parsing, and filtering follow consumption. Leaving `with` closes the resource even if the consumer takes only one record. Do not return `errors` for continued reading after the `with` block ends.

Bounded memory requires checking the entire pipeline:

- Reading line by line avoids loading the whole file, but a huge single line can still require substantial memory.
- `list(records)` and `sorted(records)` collect values and defeat streaming.
- Appending every result to a list that is never cleared defeats the benefit of an upstream generator.
- Lazy execution can defer exceptions until consumption, so error handling must cover iteration.

### 5.4 Generators Can Also Describe Resource Lifetimes

`contextlib.contextmanager` turns a generator function that yields once into a context manager: code before `yield` handles entry, code afterward handles exit, and cleanup belongs in `finally`.

```python
from collections.abc import Iterator
from contextlib import contextmanager


@contextmanager
def temporary_state(state: dict[str, bool]) -> Iterator[None]:
    previous = state["active"]
    state["active"] = True
    try:
        yield
    finally:
        state["active"] = previous


state = {"active": False}
try:
    with temporary_state(state):
        assert state["active"]
        raise RuntimeError("Simulated failure")
except RuntimeError:
    pass
assert not state["active"]
```

If a generator owns a file or connection, an early consumer `break` does not universally guarantee immediate generator closure. Manage the resource in an outer `with`, or explicitly close the generator with `contextlib.closing()`. Use `aclosing()` for async generators. [contextlib lifecycle helpers](https://docs.python.org/3.14/library/contextlib.html)

### 5.5 Async Generators: Wait for the Next Item, Then Yield

```python
import asyncio
from collections.abc import AsyncIterator
from contextlib import aclosing


async def messages() -> AsyncIterator[str]:
    try:
        for index in range(3):
            await asyncio.sleep(0.01)
            yield f"message-{index}"
    finally:
        print("Message stream closed")


async def main() -> None:
    async with aclosing(messages()) as stream:
        async for message in stream:
            assert message == "message-0"
            break


if __name__ == "__main__":
    asyncio.run(main())
```

Consume synchronous generators with `for` and async generators with `async for`. An `async def` containing `yield` returns an async generator, not an ordinary coroutine that can be directly awaited for a final result.

### 5.6 Measuring Lazy Processing with `tracemalloc`

A useful generator comparison asks whether equivalent computations retain all intermediate values, rather than merely comparing generator object sizes. This example measures peak traced Python allocations for list-based and generator-based sums:

```python
import tracemalloc
from collections.abc import Callable

LIMIT = 100_000


def list_total() -> int:
    return sum([number * number for number in range(LIMIT)])


def generator_total() -> int:
    return sum(number * number for number in range(LIMIT))


def measure(work: Callable[[], int]) -> tuple[int, int]:
    tracemalloc.start()
    try:
        result = work()
        _, peak = tracemalloc.get_traced_memory()
        return result, peak
    finally:
        tracemalloc.stop()


list_result, list_peak = measure(list_total)
generator_result, generator_peak = measure(generator_total)
expected = LIMIT * (LIMIT - 1) * (2 * LIMIT - 1) // 6
assert list_result == generator_result == expected
print(f"List peak: {list_peak / 1024:.1f} KiB")
print(f"Generator peak: {generator_peak / 1024:.1f} KiB")
```

The list version retains all squares before summing; the generator yields them individually to `sum()`. A substantial peak difference is typical here, but exact byte counts depend on interpreter, build, and environment. The example therefore asserts neither a fixed count nor a ratio.

State the measurement boundaries:

- `tracemalloc` observes tracked allocations after tracing starts. It does not equal total process RSS and should not be assumed to cover every native-library allocation.
- `sys.getsizeof(generator)` measures the object itself, not the memory of the entire pipeline.
- Intermediate lists may already be released when a function returns, so low current usage does not imply a low peak.
- Compare snapshots with `compare_to(..., "lineno")` to locate allocations that are still live. Snapshots and peak counters answer different questions.
- Tracing has overhead; measure execution time and memory separately.

Section 10 includes a snapshot exercise. [tracemalloc documentation](https://docs.python.org/3.14/library/tracemalloc.html)

## 6. Concurrency and the GIL: Identify the Bottleneck First

### 6.1 Concurrency and Parallelism Are Different

- **Concurrency:** Task lifetimes overlap, such as starting request B while waiting for A.
- **Parallelism:** Multiple execution units work at the same instant, such as two CPU cores computing separate results.
- **I/O-bound:** Much of the time is spent waiting for networks, disks, or external services.
- **CPU-bound:** Much of the time is spent computing, such as scanning, parsing, or transforming complex data in pure Python.

An event loop in one thread can manage many concurrent I/O operations, but cannot execute two Python computations in that thread on two cores simultaneously. Node.js should not be described as a process containing only one thread either; the relevant analogy is user-code scheduling on one event loop.

### 6.2 Understanding the GIL Precisely

In a **normal GIL-enabled CPython build**, only one thread in the same interpreter normally executes Python bytecode at a time. Threads therefore generally do not provide linear multi-core speedups for pure-Python CPU calculations.

Threads remain useful: blocking I/O commonly releases the GIL, and some native extensions release it during computation. Benefits depend on the layer actually performing the computation or wait. [Official GIL FAQ](https://docs.python.org/3.14/faq/library.html#can-t-we-get-rid-of-the-global-interpreter-lock)

Also distinguish two version-related facts:

1. CPython 3.13 introduced an optional free-threaded build that can run threads with the GIL disabled.
2. Installing a newer Python version does not imply that the GIL is disabled. Build configuration, runtime options, and extension compatibility matter; incompatible extensions can re-enable the GIL.

This guide's default recommendations assume a normal GIL-enabled build. A free-threaded build is a deployment choice requiring separate validation. Neither "Python threads can never run in parallel" nor "new versions have universally removed the GIL" is accurate. [Free-threading documentation](https://docs.python.org/3.14/howto/free-threading-python.html)

### 6.3 Choosing an Execution Model

| Workload | Consider first | Reason | Main costs or boundaries |
| --- | --- | --- | --- |
| Multiple requests using async network APIs | `asyncio` | Waiting can yield the event loop. | Bound concurrency, timeouts, and connections. |
| Existing synchronous I/O libraries or blocking file operations | Thread pool / `asyncio.to_thread()` | Reuse sync APIs without occupying the event-loop thread. | Threads are limited; cancelling the wait does not terminate the thread. |
| Substantial independent pure-Python computations | Multiprocessing / `ProcessPoolExecutor` | Processes can use multiple cores. | Startup, serialization, communication, and memory. |
| Native libraries that release the GIL | Check library documentation and measure threads or built-in parallelism | Computation may already run in parallel in native code. | Combining library parallelism with process pools can oversubscribe threads. |
| Very small, short, or strongly ordered tasks | Serial execution | Scheduling may cost more than it saves. | Measure before adding concurrency. |
| Computation on a free-threaded build | Evaluate threads against dependencies and measurements | The GIL assumption has changed. | Shared state and races still require care. |

Use this table for learning and initial decisions. Final choices should be supported by task duration, memory usage, and external-service capacity measurements.

### 6.4 The GIL Does Not Make Business Operations Thread-Safe

"Read balance → check balance → deduct balance" is a sequence of business operations. Protection of individual low-level operations does not make that entire sequence atomic.

Coroutines on one thread can also race: suspension between a read and write lets another task change shared state. Use `threading.Lock` for threads and `asyncio.Lock` for async tasks on the same event loop; an async lock is not a replacement for a thread lock.

```python
import asyncio


async def count_updates(use_lock: bool) -> int:
    value = 0
    lock = asyncio.Lock()

    async def update() -> None:
        nonlocal value
        if use_lock:
            async with lock:
                previous = value
                await asyncio.sleep(0)
                value = previous + 1
        else:
            previous = value
            await asyncio.sleep(0)
            value = previous + 1

    async with asyncio.TaskGroup() as group:
        for _ in range(10):
            group.create_task(update())
    return value


async def main() -> None:
    assert await count_updates(use_lock=False) == 1
    assert await count_updates(use_lock=True) == 10


if __name__ == "__main__":
    asyncio.run(main())
```

The unlocked version deliberately yields before writing so all ten tasks read the same old value, reliably demonstrating lost updates. The locked version protects the full read-modify-write interval. `sleep(0)` illustrates interleaving here; keep real critical sections short and avoid lengthy network operations while holding a lock. [asyncio synchronization primitives](https://docs.python.org/3.14/library/asyncio-sync.html)

## 7. asyncio: From Starting Tasks to Reliable Cleanup

### 7.1 Coroutine Objects, Tasks, and Futures

| Object | How it is created | What application code should know |
| --- | --- | --- |
| Coroutine function | `async def fetch(): ...` | Defines asynchronous work. |
| Coroutine object | `fetch()` | Work awaiting execution; creating it does not execute its body. |
| Task | `create_task(coro)` or `TaskGroup.create_task(coro)` | Schedules a coroutine; its result can be awaited and cancellation requested. |
| Future | Usually provided by a lower-level API | Represents a result available later; applications rarely need to create one manually. |

Calling a JS `async function` executes its body until the first suspension. Calling a native Python coroutine function normally only creates a coroutine object. Do not transfer Promise startup assumptions unchanged.

```python
import asyncio


async def load(name: str, events: list[str]) -> str:
    events.append(f"Started {name}")
    await asyncio.sleep(0.01)
    events.append(f"Finished {name}")
    return name


async def main() -> None:
    events: list[str] = []
    pending = load("A", events)
    assert events == []
    assert await pending == "A"

    async with asyncio.TaskGroup() as group:
        first = group.create_task(load("B", events))
        second = group.create_task(load("C", events))

    assert first.result() == "B"
    assert second.result() == "C"
    print(events)


if __name__ == "__main__":
    asyncio.run(main())
```

Normally A finishes before B and C proceed with overlapping lifetimes. This guide uses default task scheduling; explicit eager task factories can change creation and execution order. Correctness should not depend on an assumed ordering immediately after `create_task()`. [Coroutines and tasks](https://docs.python.org/3.14/library/asyncio-task.html#coroutines)

### 7.2 Consecutive `await` Statements Are Not Automatically Concurrent

```text
Serial:
first = await fetch("A")
second = await fetch("B")

Concurrent:
Schedule A and B with TaskGroup / create_task, then wait for both.
```

If two independent operations each wait about 0.1 seconds, serial execution usually takes roughly 0.2 seconds, while concurrent execution takes roughly 0.1 seconds plus overhead. This explains overlapping waits; it does not guarantee actual request latency.

Also, `await` does not guarantee a switch to another task every time: an operation that completes immediately may let the current task continue. Putting a large CPU loop inside `async def` does not automatically provide fair scheduling or multi-core speedups.

### 7.3 Choosing Between `gather()` and `TaskGroup`

| Dimension | `asyncio.gather()` | `asyncio.TaskGroup` |
| --- | --- | --- |
| Structure | Wait for awaitables and return a result list. | Manage related task lifetimes with `async with`. |
| Result order | Successful results follow input order. | Retain Tasks and read their individual results. |
| Default ordinary-exception behavior | Propagate the first exception; other tasks normally continue. | Cancel unfinished siblings, await cleanup, then propagate an exception group. |
| Partial failures | Use `return_exceptions=True` and inspect every result. | Handle permitted business failures inside each task; propagate unexpected errors. |
| Typical use | Existing code or independently collected results in input order. | Related child tasks that share a lifetime and need coordinated cleanup. |

Cancelling `gather()` itself differs from a child failing. `TaskGroup` also has specific rules for cancellation, `KeyboardInterrupt`, and `SystemExit`. The table is not an exhaustive exception specification. [Concurrent execution and task groups](https://docs.python.org/3.14/library/asyncio-task.html#task-groups)

This example verifies that an unexpected failure triggers sibling cleanup:

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def waiting_job() -> None:
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    async def failing_job() -> None:
        await started.wait()
        raise ValueError("Task processing failed")

    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(waiting_job())
            group.create_task(failing_job())
    except* ValueError as group_error:
        assert len(group_error.exceptions) == 1

    assert cleaned.is_set()


if __name__ == "__main__":
    asyncio.run(main())
```

`except*` handles members of an exception group by type. Handle expected types and allow other failures to remain visible. Events synchronize this example, avoiding guesses about which task starts first when verifying cancellation.

### 7.4 Bounding Concurrency with `Semaphore`

Cheap task creation does not imply unlimited database connections, HTTP connections, or external-service capacity. A semaphore limits how many tasks enter a particular operation:

```python
import asyncio


async def main() -> None:
    limit = 3
    semaphore = asyncio.Semaphore(limit)
    active = 0
    peak = 0

    async def fetch(item_id: int) -> int:
        nonlocal active, peak
        async with semaphore:
            active += 1
            peak = max(peak, active)
            try:
                await asyncio.sleep(0.01)
                return item_id * 2
            finally:
                active -= 1

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(fetch(index)) for index in range(12)]

    assert [task.result() for task in tasks] == list(range(0, 24, 2))
    assert peak == limit
    assert active == 0


if __name__ == "__main__":
    asyncio.run(main())
```

This still creates 12 Tasks. With a million inputs, only three may enter the core of `fetch`, while a million scheduled or waiting Tasks still exist.

Distinguish these limits:

- **Concurrency limit:** How many operations execute at once; a semaphore can control this.
- **Backlog limit:** How much work may queue in memory; use a bounded queue or batched submission.
- **Rate limit:** How many operations may begin per second; this needs additional rate control. Concurrency of three does not mean three operations per second.

The integrated exercise uses fixed workers and `asyncio.Queue(maxsize=...)`. When the queue fills, the producer waits in `await put()`, creating backpressure. [Semaphores](https://docs.python.org/3.14/library/asyncio-sync.html#semaphore) and [async queues](https://docs.python.org/3.14/library/asyncio-queue.html)

### 7.5 Timeouts and Cancellation Are Cooperative

```python
import asyncio


async def main() -> None:
    cleaned = asyncio.Event()

    async def stalled_request() -> None:
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    try:
        async with asyncio.timeout(0.02):
            await stalled_request()
    except TimeoutError:
        assert cleaned.is_set()
    else:
        raise AssertionError("This example must time out")


if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.timeout()` implements its deadline using cancellation; catch `TimeoutError` outside the context. Another common API, `asyncio.wait_for()`, waits for cancelled work to finish cleanup, so elapsed time can exceed its timeout. Synchronous code blocking the event loop also cannot be interrupted promptly by an async timeout. [Timeout mechanisms](https://docs.python.org/3.14/library/asyncio-task.html#timeouts)

Follow these cancellation rules:

1. Release resources in `try/finally`.
2. `CancelledError` inherits directly from `BaseException`; ordinary `except Exception` does not catch it.
3. When explicitly catching `CancelledError`, normally re-raise it after cleanup.
4. Cancellation is a request. It does not prove a remote operation was undone or a committed database write rolled back.
5. Do not prevent termination by catching `BaseException`, using a bare `except`, or retrying indefinitely.

See [asyncio exceptions](https://docs.python.org/3.14/library/asyncio-exceptions.html) for the inheritance hierarchy.

### 7.6 Integrating Synchronous I/O with Async Code

Calling `time.sleep()` or blocking file and HTTP APIs on the event-loop thread prevents other tasks on that thread from progressing. Existing synchronous I/O can run in a thread:

```python
import asyncio
from pathlib import Path
from tempfile import TemporaryDirectory


async def main() -> None:
    with TemporaryDirectory() as directory:
        path = Path(directory) / "message.txt"
        await asyncio.to_thread(path.write_text, "hello", encoding="utf-8")
        content = await asyncio.to_thread(path.read_text, encoding="utf-8")
        assert content == "hello"


if __name__ == "__main__":
    asyncio.run(main())
```

The purpose is to move blocking file operations off the event-loop thread, not to promise faster small-file reads. On a normal GIL-enabled build, do not assume `to_thread()` accelerates a large pure-Python CPU loop. Cancelling the wait also normally does not stop an already running thread function. [Running in threads](https://docs.python.org/3.14/library/asyncio-task.html#running-in-threads)

### 7.7 Applying These Lessons in Web Services

- When a framework owns the event loop, await work in async handlers instead of calling `asyncio.run()` yourself.
- Synchronous database or HTTP calls inside `async def` can still block the event loop; choose an async driver or explicitly delegate to threads.
- Client pools and concurrency budgets generally need application-level lifetimes; do not create unlimited connections per request.
- A new semaphore inside each `main()` limits only that invocation. Separate copies across requests, worker processes, or replicas add up to a higher total concurrency.
- An in-memory Task is not a durable job queue. Decide separately whether work may be lost on process exit, request cancellation, or deployment restarts.

These are judgments to develop before Stage Four, not a requirement to build a web service now.

### 7.8 Async Verification and Debugging: Expose Failures Reliably

Enable diagnostics first, then determine whether work was never started, never awaited, failed without observation, or blocked the event loop.

```bash
PYTHONASYNCIODEBUG=1 python -W default example.py
```

This command works in the macOS / Linux shell used here. Alternatively, set `asyncio.run(main(), debug=True)` at the entry point. Common signals and investigation paths include:

| Signal | Common cause | Investigation |
| --- | --- | --- |
| `coroutine ... was never awaited` | A coroutine was created but never awaited or scheduled. | Find its creation site and identify who owns execution. |
| `Task exception was never retrieved` | A failed Task's exception was never observed. | Prefer TaskGroup ownership or explicitly await and handle its result. |
| Slow-callback logs | Synchronous code occupies the event-loop thread too long. | Check blocking I/O, CPU work, and synchronous logging. |
| `ResourceWarning` | A file, connection, or other resource was not closed promptly. | Inspect context managers and exceptional exits. |

Debug mode aids diagnosis; it is not a complete correctness proof. A slow callback is also different from a slow network request: other tasks can progress during a normal async wait. [Developing and debugging asyncio](https://docs.python.org/3.14/library/asyncio-dev.html)

**When verifying cancellation, wait for the actual target state instead of sleeping for an estimated interval.**

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()
    baseline = asyncio.all_tasks()

    async def job() -> None:
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    task = asyncio.create_task(job(), name="cancellation-demo")
    try:
        async with asyncio.timeout(2):
            await started.wait()
    finally:
        task.cancel()
        try:
            await task
        except asyncio.CancelledError:
            pass

    assert task.cancelled()
    assert cleaned.is_set()
    assert asyncio.all_tasks() == baseline


if __name__ == "__main__":
    asyncio.run(main(), debug=True)
```

The event proves that the task started. The two-second timeout only prevents a hung check; it does not synchronize task progress. Handling `CancelledError` in a caller waiting for a cancelled task differs from a business coroutine swallowing cancellation and continuing to work.

**When isolating external I/O, check that it was awaited, not merely called.** Standard-library `AsyncMock` simulates async results and failures without a real service:

```python
import asyncio
from collections.abc import Awaitable, Callable
from unittest.mock import AsyncMock


async def retry_once(load: Callable[[], Awaitable[str]]) -> str:
    try:
        return await load()
    except TimeoutError:
        return await load()


async def main() -> None:
    remote = AsyncMock(side_effect=[TimeoutError("Simulated timeout"), "ready"])
    assert await retry_once(remote) == "ready"
    assert remote.await_count == 2
    remote.assert_awaited_with()

    broken = AsyncMock(side_effect=ValueError("Invalid input"))
    try:
        await retry_once(broken)
    except ValueError:
        pass
    else:
        raise AssertionError("Non-timeout errors must propagate")
    broken.assert_awaited_once_with()

    cancelled = AsyncMock(side_effect=asyncio.CancelledError())
    try:
        await retry_once(cancelled)
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("Cancellation must propagate")
    cancelled.assert_awaited_once_with()


if __name__ == "__main__":
    asyncio.run(main())
```

`retry_once` is a minimal verification example that retries one timeout once. Real retry policies also need idempotency, a total time budget, and backoff. Mocks verify caller control flow; correct real-connection cleanup still needs appropriate integration checks. [AsyncMock](https://docs.python.org/3.14/library/unittest.mock.html#unittest.mock.AsyncMock)

### 7.9 `ContextVar`: Carry Request Context Without Mixing Tasks

Request IDs in logs often need to travel across multiple function layers. Explicit parameters remain clear and effective. `ContextVar` is useful for cross-cutting logging and tracing metadata associated with the call chain.

A module global is one shared binding. `threading.local()` distinguishes threads, while one event-loop thread can serve multiple request tasks. `ContextVar` gives those tasks separate context bindings for information such as request IDs.

```python
import asyncio
from contextvars import ContextVar

request_id: ContextVar[str] = ContextVar("request_id", default="-")


async def read_request() -> str:
    await asyncio.sleep(0)
    return request_id.get()


async def handle(identifier: str) -> str:
    token = request_id.set(identifier)
    try:
        return await read_request()
    finally:
        request_id.reset(token)


async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(handle("request-a"))
        second = group.create_task(handle("request-b"))
    assert first.result() == "request-a"
    assert second.result() == "request-b"
    assert request_id.get() == "-"

    token = request_id.set("parent-before")
    try:
        async with asyncio.TaskGroup() as group:
            child = group.create_task(read_request())
            request_id.set("parent-after")
        assert child.result() == "parent-before"
        assert request_id.get() == "parent-after"
        assert await asyncio.to_thread(request_id.get) == "parent-after"
    finally:
        request_id.reset(token)
    assert request_id.get() == "-"


if __name__ == "__main__":
    asyncio.run(main())
```

This demonstrates two levels: independent tasks have isolated bindings, and a newly created child Task normally inherits the context at creation. Later changes to the parent's binding do not automatically update the child. `asyncio.to_thread()` also propagates the context when that operation executes to the worker thread, but this does not generalize to every thread or process API.

Practical rules:

- Create a `ContextVar` at module level, set it on request entry, and restore the previous binding with the corresponding token on exit.
- Put `reset()` in `try/finally` so exceptions and cancellation cannot skip restoration. This example retains Python 3.11+ compatible syntax.
- Copying context does not deep-copy its values. Different contexts may still reference the same mutable dictionary. Prefer immutable values such as strings, or explicitly create independent containers.
- `ContextVar` does not provide locking, a shared cache, or interprocess communication, and it does not replace business parameters or authorization checks.

You can add the request ID to the Section 9 logs, but do not log tokens or sensitive business objects. [ContextVar support in asyncio](https://docs.python.org/3.14/library/contextvars.html#asyncio-support)

## 8. Multiprocessing: Using Multiple CPU Cores

### 8.1 Understanding `multiprocessing` Through Task Boundaries

Each process has its own interpreter and address space, so separate processes can execute Python calculations simultaneously even on a normal GIL-enabled build. Data usually needs serialization for transfer; objects are not all directly shared as they are within one thread.

Common interfaces and responsibilities:

| Interface | Responsibility |
| --- | --- |
| `multiprocessing.Process` | Explicitly manage a child process and its startup and termination. |
| `multiprocessing.Queue` / `Pipe` | Explicitly transfer data between processes. |
| `multiprocessing.Pool` | Manage a reusable pool of computation processes. |
| `ProcessPoolExecutor` | Submit work with `submit()` or `map()` using an interface similar to a thread pool. |

For a batch of independent inputs followed by aggregation, a process pool makes task boundaries easy to see. `ProcessPoolExecutor` uses `multiprocessing`; it does not bypass process constraints. [Process pools](https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor)

### 8.2 A Runnable CPU Computation Example

Save this as `process_demo.py` and run it from a terminal. Pure Python computation highlights the execution model; for real workloads, first consider better algorithms or native-library implementations.

```python
import multiprocessing
from concurrent.futures import ProcessPoolExecutor
from time import perf_counter


def sum_squares(limit: int) -> int:
    return sum(number * number for number in range(limit))


def main() -> None:
    inputs = [200_000, 250_000, 300_000, 350_000]

    started = perf_counter()
    serial = [sum_squares(limit) for limit in inputs]
    serial_seconds = perf_counter() - started

    context = multiprocessing.get_context("spawn")
    started = perf_counter()
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        parallel = list(pool.map(sum_squares, inputs))
    parallel_seconds = perf_counter() - started

    expected = [limit * (limit - 1) * (2 * limit - 1) // 6 for limit in inputs]
    assert serial == parallel == expected
    print(f"Serial: {serial_seconds:.4f}s")
    print(f"Process pool: {parallel_seconds:.4f}s")


if __name__ == "__main__":
    main()
```

```bash
python process_demo.py
```

Inputs are deliberately small for quick verification. The process pool may be slower because timing includes startup and shutdown. For throughput comparisons, increase work per task, reuse the pool, and repeat measurements. The closed-form sum at the end also illustrates that algorithm improvements often matter more than scheduling choices.

### 8.3 Why Top-Level Functions, Main Guards, and Serializable Data Matter

- `sum_squares` is defined at module level so a child process can find it through the module.
- `if __name__ == "__main__":` prevents another pool from being created when a child imports the module.
- Arguments and results should be picklable; do not directly pass database connections, open files, or objects containing complex runtime state.
- Lambdas, local functions, and functions defined interactively are unsuitable pool tasks for this example.
- Ordinary global lists are not automatically shared. A child changing its list does not update the parent's list.
- Observe results to expose task exceptions. With `map()`, an exception may be raised while consuming the result iterator.

See [ProcessPoolExecutor documentation](https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor) for serialization restrictions and importable-main requirements.

### 8.4 Do Not Depend on the Platform's Default Start Method

The example explicitly chooses `spawn`, which starts a fresh interpreter and imports the required modules. This exposes the import and data-transfer constraints that portable process code needs to handle.

| Start method | Broad behavior | What to focus on |
| --- | --- | --- |
| `spawn` | Start a fresh interpreter. | Safe imports, main guards, and serializable arguments. |
| `fork` | Copy the parent process state. | Multithreaded parents and inherited resources introduce complications. |
| `forkserver` | A separate server forks child processes. | Availability and defaults depend on the platform and Python version. |

Windows and macOS default to `spawn`. Python 3.14 switches eligible POSIX platforms, such as Linux, to `forkserver`; `fork` is no longer the default on any platform. Do not copy old assumptions that Linux always defaults to `fork`. [Start methods and version changes](https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods)

### 8.5 Multiprocessing Also Needs Capacity Limits

More processes do not provide unlimited speed. Evaluate these factors together:

1. **Work per task:** Scheduling can dominate tiny operations; sensible batching may help.
2. **Transfer size:** Repeatedly copying large objects between processes may cost more than computation.
3. **Backlog:** Do not submit unlimited work at once. This example has only four inputs; large workloads need bounded in-flight work. Python 3.14 adds `buffersize` to `Executor.map()`, but it is outside the common 3.11+ examples here.
4. **Memory and CPU quotas:** Container CPU availability, existing service workers, and per-process memory all constrain capacity.
5. **Shutdown:** Cancelling a Future normally cannot stop computation that already started, and leaving the executor context waits for work by default.

Async services can await process-pool work through interfaces such as `run_in_executor(pool, func, ...)`. Reuse and close the pool over the application lifetime instead of creating one for every request.

### 8.6 Measure the Bottleneck Before Explaining an Optimization

Timing, profiling, and allocation tracing answer different questions:

| Tool | Question | Interpretation boundary |
| --- | --- | --- |
| `perf_counter()` | How much elapsed time did an operation take? | Includes waits and startup inside the measured interval. |
| `timeit` | How long does a short operation take across repetitions? | A microbenchmark does not represent an entire service; garbage collection is temporarily disabled by default. |
| `cProfile` | Which functions are called often, and where is time spent? | Profiling adds overhead; profiling a parent does not automatically profile child-process computation. |
| `tracemalloc` | Which tracked Python allocations remain live, and what was the peak? | It is not total process memory. |

This example compares two implementations of the same calculation and inspects call statistics:

```python
import cProfile
import io
import pstats
from timeit import repeat

LIMIT = 20_000


def loop_sum() -> int:
    return sum(number * number for number in range(LIMIT))


def formula_sum() -> int:
    return LIMIT * (LIMIT - 1) * (2 * LIMIT - 1) // 6


assert loop_sum() == formula_sum()
for work in (loop_sum, formula_sum):
    samples = repeat(work, number=10, repeat=5)
    print(work.__name__, [round(seconds / 10, 8) for seconds in samples])

profiler = cProfile.Profile()
profiler.runcall(loop_sum)
output = io.StringIO()
pstats.Stats(profiler, stream=output).strip_dirs().sort_stats("cumulative").print_stats(5)
print(output.getvalue())
```

Each printed timing is the per-call average for its batch. Repetitions expose environmental noise; do not select only one favorable sample. `cumulative` includes a function and its descendants, while `tottime` measures the function's own time. Overlapping call trees mean cumulative times should not simply be added together.

Assert equivalent results before measuring costs. When comparing serial execution, thread pools, and process pools, keep inputs and workload definitions consistent, and state whether startup, serialization, and aggregation are included. Do not attribute a better algorithm's gains to concurrency. [timeit](https://docs.python.org/3.14/library/timeit.html) and [Python profilers](https://docs.python.org/3.14/library/profile.html)

## 9. Integrated Exercise: A Bounded Async Pipeline

### 9.1 Scenario and Completion Criteria

Implement a local data-enrichment simulation: generate 12 jobs, use fixed workers to simulate external queries, let one job time out and the rest succeed, then produce a summary.

All I/O is simulated with `asyncio`; no API keys, network, or third-party packages are required. The exercise combines the four main topics in one data flow:

```text
A generator creates one Job at a time
        ↓
Bounded Queue: wait when full to limit queued work
        ↓
Fixed workers: execute async operations with timeouts
        ↓
Report: retain counts rather than all results
        ↓
__call__ reads the summary; __str__ displays it

An outer decorator measures total time; TaskGroup manages worker lifetimes
```

Completion criteria:

- Eleven successes and one timeout, totaling twelve jobs.
- No more than three simulated requests executing simultaneously.
- At most six queued items, without one Task per input.
- Timeouts counted as expected business outcomes; unexpected exceptions propagate.
- Workers have exited and the active request count is zero on normal completion.

### 9.2 Complete Example

Save as `stage3_pipeline.py`:

```python
import asyncio
from collections.abc import Awaitable, Callable, Iterator
from dataclasses import dataclass
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def measured(
    func: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(func)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            print(f"Total time: {perf_counter() - started:.4f}s")

    return wrapper


@dataclass(frozen=True)
class Job:
    item_id: int


@dataclass
class Report:
    succeeded: int = 0
    timed_out: int = 0
    active: int = 0
    peak: int = 0

    def __call__(self) -> dict[str, int]:
        return {"succeeded": self.succeeded, "timed_out": self.timed_out}

    def __str__(self) -> str:
        return (
            f"Succeeded={self.succeeded}, timed out={self.timed_out}, "
            f"peak concurrency={self.peak}"
        )


def iter_jobs(total: int) -> Iterator[Job]:
    for item_id in range(total):
        yield Job(item_id)


async def enrich(job: Job) -> int:
    if job.item_id == 7:
        await asyncio.Event().wait()  # Wait deterministically until timeout cancellation.
    await asyncio.sleep(0.01)
    return job.item_id * 10


async def worker(queue: asyncio.Queue[Job | None], report: Report) -> None:
    while True:
        job = await queue.get()
        try:
            if job is None:
                return

            report.active += 1
            report.peak = max(report.peak, report.active)
            try:
                async with asyncio.timeout(0.2):
                    result = await enrich(job)
                assert result == job.item_id * 10
                report.succeeded += 1
            except TimeoutError:
                report.timed_out += 1
            finally:
                report.active -= 1
        finally:
            queue.task_done()


@measured
async def run_pipeline() -> Report:
    worker_count = 3
    queue: asyncio.Queue[Job | None] = asyncio.Queue(maxsize=6)
    report = Report()

    async with asyncio.TaskGroup() as group:
        for _ in range(worker_count):
            group.create_task(worker(queue, report))

        for job in iter_jobs(12):
            await queue.put(job)

        for _ in range(worker_count):
            await queue.put(None)

        await queue.join()

    assert report() == {"succeeded": 11, "timed_out": 1}
    assert report.active == 0
    assert 1 <= report.peak <= worker_count
    assert queue.empty()
    return report


if __name__ == "__main__":
    print(asyncio.run(run_pipeline()))
```

```bash
python stage3_pipeline.py
```

Output contains a timing line and a summary. A normal run reaches peak concurrency of three. Assertions check business results and concurrency boundaries, not exact duration.

### 9.3 Understanding the Design

1. **The producer does not build the entire input list.** `iter_jobs()` yields one job at a time, and `queue.put()` waits when the queue is full.
2. **The number of workers is fixed.** Task count does not grow with input size. Beyond the queue, account for jobs being processed and one job the producer is waiting to enqueue.
3. **`None` is the termination signal.** Real entries are `Job` objects, so the signal is unambiguous. Each worker exits after consuming one signal.
4. **Pair every `get()` with one `task_done()`.** Include termination signals, or `join()` may wait forever for the unfinished-work count to reach zero.
5. **Expected failures and programming errors have different handling.** Timeouts update the report; assertions and other unexpected exceptions trigger TaskGroup failure cleanup.
6. **No `await` occurs inside each shared-counter update.** These short updates do not interleave through coroutine scheduling on this one event-loop thread. This is not a general thread-safety guarantee.
7. **Resource lifetimes are explicit.** All workers have finished when TaskGroup exits; the decorator records normal or exceptional duration in `finally`.

`queue.join()` means queued work has received the required `task_done()` calls; alone it does not guarantee worker exit. The outer TaskGroup supplies that guarantee here. [Queue completion accounting](https://docs.python.org/3.14/library/asyncio-queue.html#asyncio.Queue.join)

Queue capacity limits item count, not total bytes. A huge payload inside one `Job` still needs a memory budget. This example does not persist jobs, call real services, or define retries; those choices depend on business requirements.

### 9.4 Four Extension Exercises

| Exercise | Change | Required observation |
| --- | --- | --- |
| Change concurrency | Try one, three, and five workers. | Counts stay correct and peak concurrency respects worker count; the single timeout affects total duration. |
| Increase inputs | Increase the job count and update expected totals. | Task count stays fixed, the report retains only counts, and the queue remains bounded. |
| Inject a programming error | Make `enrich()` raise `ValueError` for an ID other than seven. | The caller receives an exception group, siblings are cancelled, and `queue.join()` does not hang indefinitely. |
| External cancellation | Start `run_pipeline()` in a Task, then cancel and await it. | `CancelledError` propagates, cleanup runs, and no workers remain. |

Verify the existing behavior before replacing `enrich()` with real async HTTP. Adding a database, retries, a distributed queue, and a web interface simultaneously makes failures difficult to localize.

```python
build, test, deploy = [

assert build("finished") == ("build", ("started", "finished"))
```

```python
class PoolConfig:
    def __init__(self, workers: int) -> None:
```

```python
first = AccessKey.from_permissions("team-a", permissions)
```

### 10.5 Context Isolation: Mutable Values Are Not Deep-Copied

**Task:** A parent task stores a dictionary containing its request ID in a context variable. Two child tasks must each update and read their own request ID while leaving the parent's dictionary unchanged. Explain why directly mutating the dictionary returned by `ContextVar.get()` is unsafe here.

<summary>Reference solution and explanation</summary>

```python
import asyncio
```

## 12. Common Pitfalls and Completion Checklist

### 12.1 Frontend Assumptions That Need Adjustment

| Tempting assumption | What to check instead |
| --- | --- |
| `async def` cannot block. | Does the body still perform synchronous I/O or lengthy CPU work? |
| Calling a coroutine function starts the task. | Was the coroutine awaited or wrapped in a Task? |
| Consecutive `await` statements imply concurrency. | Were independent tasks scheduled before waiting for them? |
| A failure in `gather()` cancels every sibling. | Distinguish exception propagation, outer cancellation, and TaskGroup behavior. |
| A semaphore of ten bounds memory to ten tasks. | Were many Tasks pre-created, and are queues and results bounded? |
| A timeout means the remote operation was undone. | Do the local wait, running thread, and remote operation each support cancellation? |
| The GIL removes the need for locks. | Can the full business read-modify-write sequence interleave? |
| Any function can be submitted to a process pool. | Is it importable, is its data serializable, and how does the pool shut down? |
| `yield` automatically guarantees low memory. | Does downstream code collect the stream into lists or retain every result? |
| A decorator naturally preserves a function's contract. | Are arguments, results, exceptions, metadata, and async awaiting preserved? |
| New Python versions disable the GIL by default. | Which interpreter build, runtime options, and dependencies are in use? |
| Swallowing an error and logging it makes code reliable. | Can callers detect failure, or will they receive a false success? |
| Indentation creates block scope like JS `let`. | Ordinary `if` and `for` do not create independent local scope; distinguish blocks from name binding. |
| A default list is created on every call. | Defaults are evaluated when a definition executes; is a `None` sentinel appropriate? |
| `frozen=True` means deep immutability. | Are referenced values still mutable, and are hash-participating fields hashable? |
| Copying Context prevents all object sharing. | Context bindings are copied, but their mutable values may still be shared. |
| A called Mock proves an async operation ran. | Were await counts, arguments, and exception propagation checked? |
| Low current memory means no high peak occurred. | Were current usage, peak usage, and live allocation snapshots examined separately? |

### 12.2 Self-Check Questions and Answer Points

Hide the answers first and explain each point in your own words:

| Question | Answer points |
| --- | --- |
| Why does a second `list(generator)` return an empty list? | The original generator retains its consumption position and is exhausted; create a new one. |
| Can `wraps` and `ParamSpec` replace each other? | No. One preserves runtime metadata; the other expresses static parameter relationships. |
| No output appeared after `async_fn()`. Is the event loop broken? | First check whether only a coroutine object was created without awaiting or scheduling it. |
| Why does a sync timing wrapper report almost no time for an async function? | It may measure only coroutine creation rather than await actual work. |
| What happens to an ordinary exception inside TaskGroup? | It requests sibling cancellation, waits for cleanup, and raises an exception group; special exceptions have separate rules. |
| How can one event-loop thread lose updates? | A suspension between reading and writing shared state lets another task intervene. |
| Does `Queue(maxsize=6)` eliminate memory concerns? | It bounds queued item count, not item size, in-flight work, or accumulated results. |
| Are correct but slower process-pool results proof of an implementation error? | No. Startup, serialization, and communication may outweigh parallelism gains. |
| Why can multiprocessing fail in an interactive console? | Children need importable main modules and task functions; interactive definitions do not meet the same conditions. |
| What is wrong with returning `None` from `__getattr__` for a missing attribute? | `hasattr()` may report that the attribute exists, removing the expected failure signal. |
| Why do callbacks created in a loop return its last index? | They read the same enclosing variable when called; factories or default arguments can capture independent values. |
| Why does `callback = obj.method` retain access to the original instance? | It is a bound method holding the instance, unlike an ordinary JS method detached from its receiver. |
| Why use `cls` in a classmethod constructor? | A subclass call should construct that subclass rather than a hard-coded base class. |
| Why can a frozen data class still fail to hash? | Generating a hash method does not make every field hashable; list fields still fail. |
| Why can a child rebind ContextVar independently but still affect a dictionary inside it? | Rebinding a name and mutating a shared object are different operations. |
| Why not assert a measured speedup ratio? | Hardware, load, builds, and measurement overhead affect time; assert results and report conditions. |

## 13. Suggested Order for Official References

You do not need to read every reference manual at once. Start with entries relevant to the exercises:

1. **Object behavior:** Read the [Python data model](https://docs.python.org/3.14/reference/datamodel.html), starting with `__init__`, `__call__`, `__getattr__`, and context-management protocols.
2. **Function composition:** Study `wraps` and `lru_cache` in [functools](https://docs.python.org/3.14/library/functools.html), together with [ParamSpec](https://docs.python.org/3.14/library/typing.html#typing.ParamSpec).
3. **Data flow and lifetimes:** Read the [iterator tutorial](https://docs.python.org/3.14/tutorial/classes.html#iterators), [generator and yield expressions](https://docs.python.org/3.14/reference/expressions.html#yield-expressions), and [contextlib](https://docs.python.org/3.14/library/contextlib.html).
4. **Task management:** Use [asyncio coroutines and tasks](https://docs.python.org/3.14/library/asyncio-task.html) alongside these examples to observe scheduling, failure, timeouts, and cancellation.
5. **Capacity and shared state:** Read [asyncio synchronization primitives](https://docs.python.org/3.14/library/asyncio-sync.html) and [asyncio queues](https://docs.python.org/3.14/library/asyncio-queue.html).
6. **CPU parallelism:** Read start methods and programming guidelines in [multiprocessing](https://docs.python.org/3.14/library/multiprocessing.html), followed by executors in [concurrent.futures](https://docs.python.org/3.14/library/concurrent.futures.html).
7. **Version boundaries:** Read about [free-threaded CPython](https://docs.python.org/3.14/howto/free-threading-python.html) to identify GIL-dependent conclusions and remaining thread-safety responsibilities.
8. **Binding and object sharing:** Use the [execution model](https://docs.python.org/3.14/reference/executionmodel.html), [programming FAQ](https://docs.python.org/3.14/faq/programming.html), and [copy](https://docs.python.org/3.14/library/copy.html) for closures, defaults, and copying experiments.
9. **Methods and data objects:** Start with binding, properties, and fields in the [descriptor guide](https://docs.python.org/3.14/howto/descriptor.html) and [dataclasses](https://docs.python.org/3.14/library/dataclasses.html), then consult deeper rules as needed.
10. **Async diagnosis and context:** Read [asyncio debugging](https://docs.python.org/3.14/library/asyncio-dev.html), [AsyncMock](https://docs.python.org/3.14/library/unittest.mock.html#unittest.mock.AsyncMock), and [contextvars](https://docs.python.org/3.14/library/contextvars.html).
11. **Measurement and diagnosis:** Use [tracemalloc](https://docs.python.org/3.14/library/tracemalloc.html), [timeit](https://docs.python.org/3.14/library/timeit.html), and [cProfile / pstats](https://docs.python.org/3.14/library/profile.html) to understand what each experiment measures.

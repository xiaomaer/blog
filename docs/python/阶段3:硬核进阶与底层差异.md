## 2. 从前端经验出发的概念地图

### 2.1 概念对照与阅读顺序

| JS / TS 经验 | Python 对应概念 | 迁移时需要调整的地方 |
| --- | --- | --- |
| `constructor` | `__init__` | `__init__` 初始化已有实例；实例创建主要由 `__new__` 负责 |
| `toString()` | `__str__` / `__repr__` | 用户展示与开发调试有不同入口 |
| 函数、闭包 | 函数、闭包、实现 `__call__` 的对象 | Python 对象也可以直接通过 `obj(...)` 调用 |
| `Proxy` 的属性读取拦截 | `__getattr__` / `__getattribute__` | 两者触发条件不同，不能直接等同于完整的 JS `Proxy` |
| 高阶函数、函数包装 | 装饰器 | 装饰发生在定义时；调用时执行的是装饰后的对象 |
| `Symbol.iterator`、`next()` | `__iter__`、`__next__` | Python 用 `StopIteration` 表示迭代结束 |
| `function*`、`yield` | 包含 `yield` 的 `def` | 生成器也会暂停并保留执行状态；通常只消费一次 |
| `async function`、Promise | `async def`、协程对象、Task | 调用 Python 协程函数通常只创建协程对象，不立即执行函数体 |
| `Promise.all()` | `gather()` / `TaskGroup` | 返回结果形式、异常传播与兄弟任务取消行为不能一一等同 |
| Web Worker / Node Worker | 线程或进程 | 只可类比“把工作交给其他执行单元”，内存与通信模型需要另学 |

学习顺序建议是：**对象协议 → 函数包装 → 惰性数据流 → 并发与资源管理**。本阶段先能读懂、写对，再考虑元类、自定义事件循环等更底层的主题。

### 2.2 作用域与闭包：变量在什么时候被读取

Python 的名字绑定到对象。给名字重新赋值与修改它指向的对象，是两件事。理解函数内部变量时，可以先用 LEGB 顺序理解常见查找：局部作用域、外层函数作用域、模块全局作用域、内置名称；类体与推导式等还有各自规则，不能把 LEGB 当成所有情况的完整定义。

Python 的普通 `if`、`for`、`while` 不创建新的局部作用域。函数体中只要存在对某个名字的赋值，这个名字通常就被视为局部变量，即使赋值语句位于尚未执行的分支中。需要重新绑定外层函数变量时，显式使用 `nonlocal`。[名称绑定与解析](https://docs.python.org/3.14/reference/executionmodel.html#resolution-of-names)

```python
from collections.abc import Callable


def make_counter() -> Callable[[], int]:
    count = 0

    def increment() -> int:
        nonlocal count
        count += 1
        return count

    return increment


first = make_counter()
second = make_counter()
assert first() == 1
assert first() == 2
assert second() == 1
```

`count += 1` 会读取旧值，再把新整数绑定到 `count`，所以这里需要 `nonlocal`。若只对外层列表执行 `items.append(...)`，修改的是对象内容，不是重新绑定 `items`，通常不需要 `nonlocal`。

另一个高频问题是**闭包延迟绑定**：函数在调用时读取捕获的变量，而不是默认保存创建时的值。

```python
from collections.abc import Callable


def make_handlers() -> list[Callable[[], int]]:
    handlers = []
    for index in range(3):
        handlers.append(lambda: index)
    return handlers


def make_fixed_handlers() -> list[Callable[[], int]]:
    handlers = []
    for index in range(3):
        handlers.append(lambda index=index: index)
    return handlers


assert [handler() for handler in make_handlers()] == [2, 2, 2]
assert [handler() for handler in make_fixed_handlers()] == [0, 1, 2]
```

这与 JS 的 `for (let i = ...)` 每轮创建独立绑定不同。修复版用默认参数在创建函数时保存当前整数；也可以用工厂函数创建单独的闭包。若保存的是可变对象，保存的仍然是对象引用，不是深拷贝。[闭包循环变量说明](https://docs.python.org/3.14/faq/programming.html#why-do-lambdas-defined-in-a-loop-with-different-values-all-return-the-same-result)

### 2.3 可变默认参数与浅拷贝：共享从哪里来

Python 函数的默认参数表达式在执行函数定义时求值，并非每次调用都重新求值。因此，用列表或字典作默认值可能在多次调用之间共享状态。

```python
def append_bad(value: int, bucket: list[int] = []) -> list[int]:
    bucket.append(value)
    return bucket


def append_good(value: int, bucket: list[int] | None = None) -> list[int]:
    if bucket is None:
        bucket = []
    bucket.append(value)
    return bucket


first = append_bad(1)
second = append_bad(2)
assert first is second
assert first == [1, 2]
assert append_good(1) == [1]
assert append_good(2) == [2]

provided: list[int] = []
assert append_good(3, provided) is provided
assert provided == [3]
```

这里用 `is None` 判断，不能随意换成 `bucket = bucket or []`：调用方传入的空列表也是合法容器，不应被悄悄替换。`append_bad` 是保留的错误示例，用断言展示错误行为，不应复制到业务代码。[默认值共享问题](https://docs.python.org/3.14/faq/programming.html#why-are-default-values-shared-between-objects)

赋值、浅拷贝、深拷贝也要分开：

```python
from copy import deepcopy

original = {"tags": ["python"]}
alias = original
shallow = original.copy()
deep = deepcopy(original)

assert alias is original
assert shallow is not original
assert shallow["tags"] is original["tags"]
shallow["tags"].append("asyncio")

assert original["tags"] == ["python", "asyncio"]
assert deep["tags"] == ["python"]
```

JS 的对象展开也有类似浅拷贝特征：新建外层容器，不代表嵌套对象被复制。`deepcopy()` 会递归复制可复制的对象图，但连接、文件等资源并不适合按这种方式复制。根据所有权决定需要复制到哪一层，不要用深拷贝掩盖不清晰的共享关系。[copy 文档](https://docs.python.org/3.14/library/copy.html)

## 3. 魔法方法：让对象参与语言协议

### 3.1 魔法方法不是随意命名的钩子

双下划线方法通常称为 dunder methods。Python 在执行内置操作时，会按约定查找这些特殊方法。

| 使用方式 | 相关方法 | 用途 |
| --- | --- | --- |
| `TaskBatch(...)` | `__new__`、`__init__` | 创建并初始化实例 |
| `print(batch)` / `str(batch)` | `__str__` | 面向用户的简洁表示 |
| `repr(batch)` | `__repr__` | 面向开发者的调试表示 |
| `len(batch)` | `__len__` | 容器长度 |
| `batch(prefix)` | `__call__` | 让实例成为可调用对象 |
| `for item in batch` | `__iter__` | 获取迭代器 |
| `batch[index]` | `__getitem__` | 索引或键访问 |
| `obj.missing` | `__getattr__` | 常规查找失败后的属性后备逻辑 |
| `with resource as value` | `__enter__`、`__exit__` | 确定资源的进入与退出行为 |
| `a == b` / `a + b` | `__eq__` / `__add__` 等 | 定义比较和运算语义 |

这些是协议入口，不必为了“高级”而全部实现。隐式特殊方法查找通常从类型上进行，因此应把它们定义在类上，不能指望给某个实例动态赋值 `__len__` 就改变 `len(obj)` 的行为。具体契约见 [Python 数据模型](https://docs.python.org/3.14/reference/datamodel.html#special-method-names)。

### 3.2 一个对象如何同时支持展示、调用与迭代

```python
from collections.abc import Iterator


class TaskBatch:
    def __init__(self, names: list[str]) -> None:
        self._names = tuple(names)

    def __repr__(self) -> str:
        return f"TaskBatch(names={self._names!r})"

    def __str__(self) -> str:
        return f"任务批次：共 {len(self)} 项"

    def __len__(self) -> int:
        return len(self._names)

    def __iter__(self) -> Iterator[str]:
        return iter(self._names)

    def __call__(self, prefix: str) -> list[str]:
        return [name for name in self if name.startswith(prefix)]


batch = TaskBatch(["build", "test", "typecheck"])
print(batch)
print(repr(batch))
assert len(batch) == 3
assert list(batch) == ["build", "test", "typecheck"]
assert batch("t") == ["test", "typecheck"]
assert list(batch) == list(batch)
```

这里有三个设计点：

1. 构造时把输入转换为元组，外部再修改原列表不会改变批次。
2. `__iter__` 每次返回一个新迭代器，所以同一个批次可以重复遍历。
3. `__call__` 让批次支持筛选操作，但实际业务中若 `batch.filter_by_prefix()` 更易读，普通方法同样合适。

`__repr__` 应尽量提供有用且无歧义的信息，不要求所有对象都能由其输出重新构造。日志表示中也不应包含访问令牌、密码等秘密。

### 3.3 `__getattr__` 与 `__getattribute__` 的区别

- `__getattribute__` 介入常规实例属性读取，覆盖它时很容易递归调用自身。
- `__getattr__` 只在常规属性访问以 `AttributeError` 失败后参与处理。
- 未找到的属性应继续抛出 `AttributeError`，否则 `hasattr()` 等操作会得到错误结果。

下面用一个受限配置视图演示，不将它当成通用的数据建模方案：

```python
class ConfigView:
    def __init__(self, values: dict[str, str]) -> None:
        self._values = values.copy()

    def __getattr__(self, name: str) -> str:
        try:
            return self._values[name]
        except KeyError as exc:
            raise AttributeError(name) from exc


config = ConfigView({"region": "local"})
assert config.region == "local"
assert not hasattr(config, "missing")
assert getattr(config, "missing", "fallback") == "fallback"
```

已有属性优先，因此与方法名或内部字段冲突的配置键不一定能通过点号访问。固定结构的业务对象通常更适合显式属性或 `dataclass`；不要为了省几个中括号牺牲类型提示与可读性。

### 3.4 上下文管理器：把清理与使用放在一起

前端常在 `try/finally` 中释放资源。Python 的 `with` 把这种生命周期封装成协议：进入时获取资源，退出时清理，包括代码块抛出异常的情况。

```python
from types import TracebackType


class Session:
    def __init__(self) -> None:
        self.closed = True

    def __enter__(self) -> "Session":
        self.closed = False
        return self

    def __exit__(
        self,
        exc_type: type[BaseException] | None,
        exc_value: BaseException | None,
        traceback: TracebackType | None,
    ) -> None:
        self.closed = True


session = Session()
try:
    with session as active:
        assert active is session
        assert not active.closed
        raise ValueError("模拟业务失败")
except ValueError:
    pass
assert session.closed
```

`as active` 接收的是 `__enter__` 的返回值。`__exit__` 返回真值会抑制块内异常；本例返回 `None`，所以异常继续传播。只有 `__enter__` 成功后，才会由 `with` 安排对应的退出调用；进入阶段的部分初始化失败，需要进入逻辑自己处理。

文件、连接、锁的释放应采用明确的生命周期，不依赖 `__del__` 或“等垃圾回收”。异步资源对应 `async with`、`__aenter__`、`__aexit__`。

### 3.5 运算符重载与元编程的学习边界

知道 `__add__` 可以定制 `+`，不意味着普通业务对象都应该重载运算符。只有语义自然、读者能预测结果时再使用。

实现值相等比较时，还要考虑哈希契约：相等对象必须有相同哈希；作为字典键或集合元素的对象，参与哈希的状态不能随意改变。不支持的运算对象通常返回 `NotImplemented`，让解释器尝试后续分派；它不同于抛出 `NotImplementedError`。

下面继续学习方法绑定、`property` 和基础描述符。元类深度定制可以延后；当前目标是读懂常见对象行为，并能解释自己实现的每个方法为什么存在。

### 3.6 方法绑定：`self`、类属性与三种方法

Python 实例方法的第一个参数通常命名为 `self`。通过实例取得普通方法时，会得到绑定方法，其中保存了实例；之后把该方法交给别处调用，实例绑定仍然存在。它与 JS 中普通函数的 `this` 由调用方式决定的机制不同。

| 方法形式 | 自动传入什么 | 适合表达什么 |
| --- | --- | --- |
| 普通实例方法 | 当前实例 `self` | 读取或修改某个对象的状态 |
| `@classmethod` | 当前类 `cls` | 替代构造入口、需要识别子类的操作 |
| `@staticmethod` | 不自动传入实例或类 | 与类相关但不依赖实例、类状态的辅助函数 |

```python
class User:
    def __init__(self, name: str) -> None:
        self.name = name

    def greet(self) -> str:
        return f"你好，{self.name}"

    @staticmethod
    def normalize(name: str) -> str:
        return name.strip().lower()

    @classmethod
    def from_text(cls, text: str) -> "User":
        return cls(cls.normalize(text))


class Admin(User):
    pass


user = User.from_text(" Mia ")
callback = user.greet
assert callback.__self__ is user
assert callback() == "你好，mia"
assert User.greet(user) == callback()
assert isinstance(Admin.from_text(" Root "), Admin)
```

工厂方法用 `cls(...)`，因此由子类调用时可创建子类实例。若辅助逻辑不属于某个类的概念范围，直接写模块函数即可，无须为了组织代码强行加 `staticmethod`。[函数与方法绑定](https://docs.python.org/3.14/howto/descriptor.html#functions-and-methods)

类属性还有共享状态问题。下面先展示错误模式，再展示每个实例拥有独立列表的写法：

```python
class SharedLabels:
    labels: list[str] = []


left = SharedLabels()
right = SharedLabels()
left.labels.append("python")
assert right.labels == ["python"]
assert left.labels is right.labels


class OwnLabels:
    def __init__(self) -> None:
        self.labels: list[str] = []


first = OwnLabels()
second = OwnLabels()
first.labels.append("python")
assert second.labels == []
```

`left.labels.append()` 修改了从类上找到的那个列表，并没有给 `left` 新建列表。实例赋值 `left.labels = [...]` 则是另一种操作。固定配置可以放在类上；每个实例自己的可变数据应在实例初始化时创建。

### 3.7 `property` 与描述符：属性读取也可以执行逻辑

`property` 与前端熟悉的 getter / setter 类似，适合把校验或计算附着在清晰的属性语义上。

```python
class WorkerConfig:
    def __init__(self, workers: int) -> None:
        self.workers = workers

    @property
    def workers(self) -> int:
        return self._workers

    @workers.setter
    def workers(self, value: int) -> None:
        if value <= 0:
            raise ValueError("worker 数量必须大于零")
        self._workers = value


config = WorkerConfig(3)
assert config.workers == 3
try:
    config.workers = 0
except ValueError:
    pass
else:
    raise AssertionError("非法数量应被拒绝")
assert config.workers == 3
```

这里的类型提示约定调用方传入整数；它并不自动提供通用的外部输入验证。把网络请求、昂贵查询隐藏在普通属性读取中，也会使成本难以判断，设计 API 时应让调用者能预期行为。

当同一种属性规则需要在多个字段或类中复用时，可以进一步理解描述符。描述符通常放在类属性上，通过 `__get__`、`__set__` 等方法参与访问：

```python
class Positive:
    def __set_name__(self, owner: type, name: str) -> None:
        self.storage_name = f"_{name}"

    def __get__(self, instance: object | None, owner: type | None = None):
        if instance is None:
            return self
        return getattr(instance, self.storage_name)

    def __set__(self, instance: object, value: int) -> None:
        if value <= 0:
            raise ValueError("数值必须大于零")
        setattr(instance, self.storage_name, value)


class Limits:
    workers = Positive()
    capacity = Positive()

    def __init__(self, workers: int, capacity: int) -> None:
        self.workers = workers
        self.capacity = capacity


first = Limits(3, 6)
second = Limits(1, 2)
assert first.workers == 3
assert first.capacity == 6
assert second.workers == 1
assert isinstance(Limits.workers, Positive)
```

描述符实例保存的是字段规则和存储位置，值放在各个业务实例上；如果把值直接存在 `Positive` 对象里，就可能错误地在所有 `Limits` 实例之间共享。

对常规实例属性查找，可用下面的简化顺序帮助理解：**数据描述符 → 实例属性字典 → 非数据描述符或其他类属性 → 失败后的 `__getattr__`**。类属性的查找还涉及继承顺序，覆盖 `__getattribute__` 也会影响行为。定义 `__set__` 或 `__delete__` 的描述符属于数据描述符；普通函数实现的方法绑定属于非数据描述符的典型用途。[描述符访问规则](https://docs.python.org/3.14/howto/descriptor.html#invocation-from-an-instance)

### 3.8 `dataclass`：字段、相等与哈希要一起设计

`dataclass` 按字段定义生成常用方法，可以减少 `__init__`、`__repr__`、`__eq__` 的重复代码。它不是运行时数据校验器，也不是直接等同于 TS `interface` 的类型声明。

```python
from dataclasses import FrozenInstanceError, dataclass, field


@dataclass
class User:
    name: str
    tags: list[str] = field(default_factory=list)


first = User("Mia")
second = User("Mia")
assert first == second
assert first is not second
assert first.tags is not second.tags
first.tags.append("python")
assert first != second
assert User.__hash__ is None


@dataclass(frozen=True)
class CacheKey:
    tenant: str
    tags: tuple[str, ...]


key = CacheKey("team-a", ("python",))
same_key = CacheKey("team-a", ("python",))
assert key == same_key
assert hash(key) == hash(same_key)
assert len({key, same_key}) == 1


@dataclass(frozen=True)
class FrozenLabels:
    tags: list[str] = field(default_factory=list)


labels = FrozenLabels()
labels.tags.append("still mutable")
assert labels.tags == ["still mutable"]
try:
    labels.tags = []
except FrozenInstanceError:
    pass
else:
    raise AssertionError("冻结字段不应允许重新赋值")

try:
    hash(labels)
except TypeError:
    pass
else:
    raise AssertionError("参与哈希的列表字段不可哈希")
```

从例子中记住四件事：

1. `default_factory=list` 在需要默认值时创建列表，避免多个实例共用可变默认值。
2. 默认生成的相等比较基于字段，且要求双方类型一致；值相等不代表是同一对象。
3. 默认 `eq=True, frozen=False` 的数据类不可哈希；`eq=True, frozen=True` 通常生成哈希方法，但参与计算的字段也必须可哈希。
4. `frozen=True` 限制字段重新赋值，不会递归冻结字段指向的对象。它不同于深度不可变，也不同于只在静态检查阶段生效的 TS `readonly`。

不要用 `unsafe_hash=True` 掩盖可变键设计问题。需要稳定缓存键时，优先选择明确的不可变字段组合。[dataclass 参数与字段规则](https://docs.python.org/3.14/library/dataclasses.html)

## 4. 装饰器：组合行为并保留函数契约

### 4.1 先把 `@` 还原为函数调用

下面的等价关系最值得记住：

```text
@decorate
def handle(...): ...

相当于：
def handle(...): ...
handle = decorate(handle)
```

装饰器接受被装饰对象，返回替代对象；常见函数装饰器返回一个包装函数，也可以注册原函数后直接返回它。装饰器不是必须生成新函数。

函数定义执行到这里时就会应用装饰器，常见时机是模块导入。不要把“定义时注册路由”和“每次请求时执行鉴权”混为一谈。[函数定义与装饰器语义](https://docs.python.org/3.14/reference/compound_stmts.html#function-definitions)

### 4.2 与 TypeScript 装饰器怎样对齐

Python 装饰器最直接的类比是 JS 高阶函数，例如 `withLogging(handler)`。TS 中以 `@` 修饰类或成员的装饰器，在调用参数、上下文和可装饰位置方面有自己的规则。

TS 5.0 引入的装饰器支持与旧的 `experimentalDecorators` 模式存在差异；学习 Python 时不应直接套用 NestJS 等项目中使用的旧装饰器签名或元数据假设。[TypeScript 5.0 装饰器说明](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html#decorators)

### 4.3 带参数、保留类型信息的同步装饰器

下面实现 `@timed("标签")`。三层函数各自只承担一件事：接收配置、接收原函数、处理每次调用。

```python
from collections.abc import Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def timed(label: str) -> Callable[[Callable[P, R]], Callable[P, R]]:
    def decorate(func: Callable[P, R]) -> Callable[P, R]:
        @wraps(func)
        def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
            started = perf_counter()
            try:
                return func(*args, **kwargs)
            finally:
                elapsed = perf_counter() - started
                print(f"{label}: {elapsed:.6f}s")

        return wrapper

    return decorate


@timed("求和")
def add(left: int, right: int = 1) -> int:
    """返回两个整数之和。"""
    return left + right


assert add(2, right=3) == 5
assert add.__name__ == "add"
assert add.__doc__ == "返回两个整数之和。"
```

注意这里的职责分工：

- `*args`、`**kwargs` 负责转发调用参数；`return` 负责保留返回值。
- `try/finally` 让成功和异常调用都记录耗时，同时允许异常传播。
- `wraps` 保留名称、文档等元数据，并设置 `__wrapped__` 供内省工具追踪；它不负责静态类型检查。
- `ParamSpec` 描述整组参数，`TypeVar` 描述返回值，让类型检查器理解包装前后的调用契约。

类型标注本身不会在运行时验证参数。查阅 [ParamSpec](https://docs.python.org/3.14/library/typing.html#typing.ParamSpec) 与 [functools.wraps](https://docs.python.org/3.14/library/functools.html#functools.wraps) 时，要区分静态契约与运行时元数据。

### 4.4 多个装饰器的顺序

```text
@outer
@inner
def work(): ...

等价于 work = outer(inner(work))

若两个包装器都先执行前置逻辑，再调用内部函数，最后执行后置逻辑：
outer 前置 → inner 前置 → work → inner 后置 → outer 后置
```

装饰器表达式按从上到下的顺序求值，结果从内到外应用。对带参数装饰器而言，“工厂什么时候执行”和“包装器什么时候执行”也要分开理解。

这会影响实际行为：缓存放在鉴权外层，缓存命中时可能绕过内层鉴权；计时放在缓存内层，只会记录未命中时的计算。安排顺序前，先写出期望的调用链。

### 4.5 标准缓存装饰器与边界

```python
from functools import lru_cache


@lru_cache(maxsize=128)
def normalize_tag(tag: str) -> str:
    return tag.strip().lower()


assert normalize_tag(" Python ") == "python"
assert normalize_tag(" Python ") == "python"
assert normalize_tag.cache_info().hits == 1
normalize_tag.cache_clear()
assert normalize_tag.cache_info().currsize == 0
```

缓存之前先回答：

1. 参数是否可哈希？列表、字典通常不能直接作为这种缓存的键。
2. 同样参数是否应得到可复用的结果？当前时间、随机值、外部可变状态未必适合。
3. 结果是否含可变对象？调用方修改缓存中的列表，会影响后续读取。
4. 是否需要过期时间、跨进程共享或按用户隔离？`lru_cache` 本身不提供这些业务能力。

不要直接用 `lru_cache` 装饰 `async def`：那样缓存的是协程对象，而不是等待完成后的结果。已经完成的原生协程不能再次执行。[缓存适用范围](https://docs.python.org/3.14/library/functools.html#functools.lru_cache)

### 4.6 异步函数需要等待实际工作

同步计时包装器若直接调用异步函数，只量到了创建协程对象的时间。下面的版本在包装器内部 `await` 原函数，才覆盖实际执行过程：

```python
import asyncio
from collections.abc import Awaitable, Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def async_timed(
    func: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(func)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            print(f"{func.__name__}: {perf_counter() - started:.4f}s")

    return wrapper


@async_timed
async def load_title() -> str:
    await asyncio.sleep(0.01)
    return "Python"


async def main() -> None:
    assert await load_title() == "Python"


if __name__ == "__main__":
    asyncio.run(main())
```

以后实现重试装饰器时，要显式限定可重试异常、次数与退避时间，确认操作具有幂等性；异步等待使用 `asyncio.sleep()`。不要捕获所有异常并无限重试，更不能吞掉任务取消。

## 5. 迭代器与生成器：按需处理数据

### 5.1 三个概念分开记

| 概念 | 表示什么 | 典型例子 |
| --- | --- | --- |
| 可迭代对象 `Iterable` | 能通过 `iter(obj)` 获取迭代器 | 列表、元组、本文的 `TaskBatch` |
| 迭代器 `Iterator` | 有当前消费位置，支持 `next()` | `iter([1, 2, 3])`、文件对象 |
| 生成器 `Generator` | 由生成器函数或表达式产生的特殊迭代器 | `(n * 2 for n in range(3))` |

迭代器也是可迭代对象，但可迭代对象不一定是迭代器。迭代器的 `__iter__()` 返回自身；`__next__()` 在没有下一个值时抛出 `StopIteration`。`for` 循环会处理这个结束信号。[迭代器与生成器教程](https://docs.python.org/3.14/tutorial/classes.html#iterators)

```python
class Countdown:
    def __init__(self, start: int) -> None:
        self.current = start

    def __iter__(self) -> "Countdown":
        return self

    def __next__(self) -> int:
        if self.current <= 0:
            raise StopIteration
        value = self.current
        self.current -= 1
        return value


counter = Countdown(3)
assert iter(counter) is counter
assert next(counter) == 3
assert list(counter) == [2, 1]
assert list(counter) == []
```

最后一行不是 bug：迭代器已经耗尽。想重新消费，需要重新创建；不能把所有 `Iterable` 都当成可重复读取的列表。

### 5.2 用 `yield` 保存执行现场

```python
from collections.abc import Iterator


def countdown(start: int) -> Iterator[int]:
    while start > 0:
        yield start
        start -= 1


items = countdown(3)
assert next(items) == 3
assert next(items) == 2
assert next(items) == 1
assert next(items, "结束") == "结束"
```

调用 `countdown(3)` 先得到生成器对象；第一次 `next()` 才开始执行函数体。运行到 `yield` 时产出一个值并暂停；下次恢复时，从暂停点继续。

- `yield value`：暂停并产出值，保留局部状态。
- `return`：结束生成器，不再产出值。
- `yield from other`：把迭代委托给另一个可迭代对象，也能传递生成器协议中的部分交互。
- `send()`、`throw()`、`close()`：可向生成器发送值、注入异常或关闭；本阶段优先掌握普通迭代与关闭。

生成器内部结束时使用 `return`，不要手动抛出 `StopIteration`。`yield` 也不等于异步：一个生成器完全可以执行阻塞式文件读取。[yield 表达式](https://docs.python.org/3.14/reference/expressions.html#yield-expressions)

### 5.3 流式读取 JSON Lines 文件

假设每行是一个 JSON 对象，我们希望筛选错误日志。让调用方拥有文件生命周期，生成器只负责解析，可以减少“生成器还没消费完，文件已经关了”的问题。

```python
import json
from collections.abc import Iterable, Iterator
from pathlib import Path
from tempfile import TemporaryDirectory
from typing import Any


def parse_jsonl(lines: Iterable[str]) -> Iterator[dict[str, Any]]:
    for line_number, line in enumerate(lines, start=1):
        if not line.strip():
            continue
        record = json.loads(line)
        if not isinstance(record, dict):
            raise ValueError(f"第 {line_number} 行必须是 JSON 对象")
        yield record


with TemporaryDirectory() as directory:
    path = Path(directory) / "events.jsonl"
    path.write_text(
        '{"level": "info", "message": "started"}\n'
        '{"level": "error", "message": "failed"}\n',
        encoding="utf-8",
    )

    with path.open(encoding="utf-8") as source:
        errors = (
            row for row in parse_jsonl(source) if row.get("level") == "error"
        )
        first = next(errors)
        assert first["message"] == "failed"

    assert source.closed
```

这里读取、解析、过滤按消费进度进行。资源离开 `with` 就会关闭，即使消费者只取一条。不要将 `errors` 返回给 `with` 外的代码继续读取。

内存是否有界要检查整个链路：

- 按行读取避免整文件加载，但单行过大仍然需要较多内存。
- `list(records)`、`sorted(records)` 会收集数据，破坏原先的流式特点。
- 如果把每条结果追加到一个永不清空的列表，前面使用生成器也无济于事。
- 惰性执行意味着异常可能在消费时才发生，错误处理应覆盖迭代过程。

### 5.4 生成器也能表达资源生命周期

`contextlib.contextmanager` 把一个只 `yield` 一次的生成器函数转换为上下文管理器：`yield` 之前负责进入，之后负责退出；资源清理放在 `finally` 中。

```python
from collections.abc import Iterator
from contextlib import contextmanager


@contextmanager
def temporary_state(state: dict[str, bool]) -> Iterator[None]:
    previous = state["active"]
    state["active"] = True
    try:
        yield
    finally:
        state["active"] = previous


state = {"active": False}
try:
    with temporary_state(state):
        assert state["active"]
        raise RuntimeError("模拟失败")
except RuntimeError:
    pass
assert not state["active"]
```

如果生成器自己持有文件或连接，消费者提前 `break` 并不构成通用的“立即关闭生成器”保证。应让外层 `with` 管理资源，或使用 `contextlib.closing()` 显式关闭生成器；异步生成器对应 `aclosing()`。[contextlib 生命周期工具](https://docs.python.org/3.14/library/contextlib.html)

### 5.5 异步生成器：等待下一项，再产出

```python
import asyncio
from collections.abc import AsyncIterator
from contextlib import aclosing


async def messages() -> AsyncIterator[str]:
    try:
        for index in range(3):
            await asyncio.sleep(0.01)
            yield f"message-{index}"
    finally:
        print("消息流已关闭")


async def main() -> None:
    async with aclosing(messages()) as stream:
        async for message in stream:
            assert message == "message-0"
            break


if __name__ == "__main__":
    asyncio.run(main())
```

同步生成器用 `for` 消费，异步生成器用 `async for` 消费。`async def` 中包含 `yield` 时，调用结果是异步生成器，不是一个可以直接 `await` 得到最终返回值的普通协程。

### 5.6 用 `tracemalloc` 验证惰性处理的内存特征

学习生成器时，比较“计算了同样的结果，却是否保留全部中间值”比比较生成器对象本身的大小更有意义。下面分别测量列表求和与生成器求和的 Python 内存分配峰值：

```python
import tracemalloc
from collections.abc import Callable

LIMIT = 100_000


def list_total() -> int:
    return sum([number * number for number in range(LIMIT)])


def generator_total() -> int:
    return sum(number * number for number in range(LIMIT))


def measure(work: Callable[[], int]) -> tuple[int, int]:
    tracemalloc.start()
    try:
        result = work()
        _, peak = tracemalloc.get_traced_memory()
        return result, peak
    finally:
        tracemalloc.stop()


list_result, list_peak = measure(list_total)
generator_result, generator_peak = measure(generator_total)
expected = LIMIT * (LIMIT - 1) * (2 * LIMIT - 1) // 6
assert list_result == generator_result == expected
print(f"列表峰值：{list_peak / 1024:.1f} KiB")
print(f"生成器峰值：{generator_peak / 1024:.1f} KiB")
```

列表版本会先保留所有平方值，生成器版本逐个产出并交给 `sum()`。在这个例子中，通常能看到明显的峰值差异；不同解释器、构建方式与环境的具体字节数不必一致，因此没有设置固定数值或倍率断言。

测量时要说明边界：

- `tracemalloc` 观察其启动后追踪到的内存分配，不等同于操作系统看到的完整进程 RSS，也不能默认覆盖所有原生库分配。
- `sys.getsizeof(generator)` 只看对象本身，不能代表整个数据流占用的内存。
- 函数结束时中间列表可能已释放，因此“当前占用很小”不等于“峰值很小”。
- 要定位仍存活的分配，可以对比前后快照的 `compare_to(..., "lineno")`；快照与峰值计数回答的是不同问题。
- 开启追踪会影响运行成本；测时间与测内存宜分开进行。

练习中的快照示例见第 10 节。[tracemalloc 文档](https://docs.python.org/3.14/library/tracemalloc.html)

## 6. 并发模型与 GIL：先判断瓶颈

### 6.1 并发和并行不是同一件事

- **并发：** 多个任务的生命周期重叠。例如等待接口 A 返回时，继续发起接口 B。
- **并行：** 多个执行单元在同一时刻实际做工作。例如两个 CPU 核心分别执行一部分计算。
- **I/O 密集：** 大量时间在等网络、磁盘或外部服务。
- **CPU 密集：** 大量时间在执行计算，例如用纯 Python 扫描、解析和变换复杂数据。

一个线程里的事件循环可以处理许多并发 I/O，但不能让同一线程中的两段 Python 计算同时占用两个核心。Node.js 也不能简单概括成“整个进程只有一个线程”；这里类比的是单个事件循环上用户代码的调度方式。

### 6.2 GIL 应怎样准确理解

在**启用 GIL 的普通 CPython 构建**中，同一解释器内通常只有一个线程可以在同一时刻执行 Python 字节码。因此，多线程通常不能让纯 Python CPU 计算按核心数线性加速。

这并不意味着 Python 线程没有价值：阻塞 I/O 通常会释放 GIL，一些原生扩展在计算时也会释放 GIL。线程是否有收益，要看真正执行计算或等待的那一层。[Python 官方 GIL FAQ](https://docs.python.org/3.14/faq/library.html#can-t-we-get-rid-of-the-global-interpreter-lock)

还需要区分两个版本事实：

1. 自 CPython 3.13 起，有可选的 free-threaded 构建，可以在关闭 GIL 的情况下运行线程。
2. 安装较新版本不等于已经关闭 GIL；构建方式、运行选项和扩展兼容性都有关。不兼容的扩展还可能重新启用 GIL。

所以本文的默认选型基于普通 GIL 构建。free-threaded 属于需要单独验证的部署选择，不能把“Python 永远不能多线程并行”或“新版本已经全面取消 GIL”当成结论。[free-threading 官方说明](https://docs.python.org/3.14/howto/free-threading-python.html)

### 6.3 执行模型选择表

| 任务情况 | 优先考虑 | 为什么 | 主要成本或边界 |
| --- | --- | --- | --- |
| 多个支持异步接口的网络请求 | `asyncio` | 等待时可让出事件循环 | 必须控制并发、超时和连接数量 |
| 现有同步 I/O 库、阻塞式文件操作 | 线程池 / `asyncio.to_thread()` | 复用同步接口，避免占住事件循环 | 线程数有限；取消等待不等于终止线程 |
| 可拆分的纯 Python 大计算 | 多进程 / `ProcessPoolExecutor` | 不同进程可使用多个核心 | 启动、序列化、进程间通信和内存开销 |
| 释放 GIL 的原生计算库 | 先查库文档并实测线程或库自身并行 | 计算可能已在原生层并行 | 与进程池叠加可能造成过量线程 |
| 很小、很短或高度依赖顺序的任务 | 直接串行 | 调度成本可能大于收益 | 先测量，不必强行并发 |
| free-threaded 构建中的计算 | 依据依赖兼容性和实测结果评估线程 | GIL 前提已变化 | 仍需处理共享状态与竞争条件 |

这个表用于学习和初步判断。最终选择应有任务耗时、内存、外部服务容量等数据支持。

### 6.4 GIL 不提供业务级线程安全

“读取余额 → 判断余额 → 扣减余额”是一组业务步骤。即使每个底层操作都有某种保护，也不能据此认定整个业务步骤原子化。

同样，一个线程的协程也会有竞争条件：只要读与写之间发生挂起，另一个任务就可能改变共享状态。线程用 `threading.Lock`，同一事件循环内的异步任务用 `asyncio.Lock`；异步锁不能代替线程锁。

```python
import asyncio


async def count_updates(use_lock: bool) -> int:
    value = 0
    lock = asyncio.Lock()

    async def update() -> None:
        nonlocal value
        if use_lock:
            async with lock:
                previous = value
                await asyncio.sleep(0)
                value = previous + 1
        else:
            previous = value
            await asyncio.sleep(0)
            value = previous + 1

    async with asyncio.TaskGroup() as group:
        for _ in range(10):
            group.create_task(update())
    return value


async def main() -> None:
    assert await count_updates(use_lock=False) == 1
    assert await count_updates(use_lock=True) == 10


if __name__ == "__main__":
    asyncio.run(main())
```

无锁版本在写入前主动让出执行权，使十个任务都读到相同旧值，稳定展示丢失更新。有锁版本保护整个读写区间。这里的 `sleep(0)` 是为了展示交错；真实业务应尽量缩短临界区，避免在持锁期间执行漫长的网络操作。[asyncio 同步原语](https://docs.python.org/3.14/library/asyncio-sync.html)

## 7. asyncio：从启动任务到可靠收尾

### 7.1 协程对象、Task、Future 各是什么

| 对象 | 如何产生 | 应用层需要知道什么 |
| --- | --- | --- |
| 协程函数 | `async def fetch(): ...` | 定义异步工作 |
| 协程对象 | `fetch()` | 一份尚待执行的工作；创建它不等于执行函数体 |
| Task | `create_task(coro)` 或 `TaskGroup.create_task(coro)` | 把协程交给事件循环调度，可等待结果、请求取消 |
| Future | 通常由底层 API 提供 | 表示一个稍后完成的结果，日常业务通常不必手动创建 |

JS 调用 `async function` 时，函数体会执行到首次挂起；Python 调用原生协程函数通常只创建协程对象。不要把 JS Promise 的启动直觉原样带过来。

```python
import asyncio


async def load(name: str, events: list[str]) -> str:
    events.append(f"开始 {name}")
    await asyncio.sleep(0.01)
    events.append(f"完成 {name}")
    return name


async def main() -> None:
    events: list[str] = []
    pending = load("A", events)
    assert events == []
    assert await pending == "A"

    async with asyncio.TaskGroup() as group:
        first = group.create_task(load("B", events))
        second = group.create_task(load("C", events))

    assert first.result() == "B"
    assert second.result() == "C"
    print(events)


if __name__ == "__main__":
    asyncio.run(main())
```

正常情况下，A 先完整执行，B、C 再交错推进。本文采用默认任务调度方式；显式启用 eager task factory 等机制时，Task 创建时机与执行顺序可能变化，不应依赖“`create_task()` 之后某段代码一定先执行”来保证正确性。[协程与任务](https://docs.python.org/3.14/library/asyncio-task.html#coroutines)

### 7.2 连续 `await` 不会自动并发

```text
串行：
first = await fetch("A")
second = await fetch("B")

并发：
先通过 TaskGroup / create_task 调度 A 和 B，再等待它们完成。
```

如果两项独立工作各等待约 0.1 秒，串行通常接近 0.2 秒，并发通常接近 0.1 秒再加调度开销。这只是对等待重叠的解释，不是对真实网络请求的耗时保证。

另外，`await` 不保证每次都把执行权交给其他任务：被等待的操作若可以立即完成，当前任务可能继续运行。把 CPU 大循环放进 `async def`，不会自动得到公平调度或多核加速。

### 7.3 `gather()` 与 `TaskGroup` 的选择

| 维度 | `asyncio.gather()` | `asyncio.TaskGroup` |
| --- | --- | --- |
| 组织形式 | 等待一组 awaitable，得到结果列表 | 用 `async with` 管理一组任务的生命周期 |
| 结果顺序 | 成功时按输入顺序排列 | 自己保留 Task，再读取各 Task 的结果 |
| 默认普通异常行为 | 将首次异常传播给等待者，其他任务通常继续执行 | 取消其他未完成任务，等待收尾，再传播异常组 |
| 收集部分失败 | `return_exceptions=True`，调用方检查每一项 | 在单个任务内处理允许的业务失败；意外异常仍向外传播 |
| 常见用途 | 已有代码或需要按输入顺序收集独立结果 | 一批有共同生命周期、需要统一收尾的子任务 |

`gather()` 本身被取消与其中一个子任务失败，行为并不相同。`TaskGroup` 对取消以及 `KeyboardInterrupt`、`SystemExit` 也有专门规则；不要把表格当成所有异常情况的完整定义。[并发执行与任务组](https://docs.python.org/3.14/library/asyncio-task.html#task-groups)

下面验证意外失败会触发兄弟任务的清理：

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def waiting_job() -> None:
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    async def failing_job() -> None:
        await started.wait()
        raise ValueError("任务处理失败")

    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(waiting_job())
            group.create_task(failing_job())
    except* ValueError as group_error:
        assert len(group_error.exceptions) == 1

    assert cleaned.is_set()


if __name__ == "__main__":
    asyncio.run(main())
```

`except*` 用于按类型处理异常组中的异常。只处理预期的类型，让其他错误继续暴露。示例使用事件同步，避免靠“猜测两个任务谁先启动”验证取消行为。

### 7.4 限制并发：`Semaphore`

发起任务很便宜，不代表数据库连接、HTTP 连接或外部服务容量无限。用信号量约束实际进入某段操作的任务数量：

```python
import asyncio


async def main() -> None:
    limit = 3
    semaphore = asyncio.Semaphore(limit)
    active = 0
    peak = 0

    async def fetch(item_id: int) -> int:
        nonlocal active, peak
        async with semaphore:
            active += 1
            peak = max(peak, active)
            try:
                await asyncio.sleep(0.01)
                return item_id * 2
            finally:
                active -= 1

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(fetch(index)) for index in range(12)]

    assert [task.result() for task in tasks] == list(range(0, 24, 2))
    assert peak == limit
    assert active == 0


if __name__ == "__main__":
    asyncio.run(main())
```

但这里仍创建了 12 个 Task。将输入改成一百万个，虽然只有 3 个进入 `fetch` 的核心区域，仍可能创建一百万个待执行或等待中的 Task。

因此要区分：

- **并发上限：** 同时执行多少项工作，信号量适合控制它。
- **积压上限：** 最多允许多少项工作在内存中排队，需要有界队列或分批提交。
- **速率上限：** 每秒最多开始多少项工作，需要额外的速率控制；并发数为 3 不等于每秒 3 次。

综合实战将使用固定 worker 加 `asyncio.Queue(maxsize=...)`。队列满时，生产者的 `await put()` 会等待，形成背压。[信号量](https://docs.python.org/3.14/library/asyncio-sync.html#semaphore) 与 [异步队列](https://docs.python.org/3.14/library/asyncio-queue.html)

### 7.5 超时与取消：是协作式控制，不是强制打断

```python
import asyncio


async def main() -> None:
    cleaned = asyncio.Event()

    async def stalled_request() -> None:
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    try:
        async with asyncio.timeout(0.02):
            await stalled_request()
    except TimeoutError:
        assert cleaned.is_set()
    else:
        raise AssertionError("本例应发生超时")


if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.timeout()` 在内部通过取消实现超时控制，在上下文外捕获 `TimeoutError`。`asyncio.wait_for()` 也是常用入口，但会等待被取消的操作完成清理，因此实际耗时可能超过给定时间。阻塞事件循环的同步代码，也无法被异步超时准时打断。[超时机制](https://docs.python.org/3.14/library/asyncio-task.html#timeouts)

处理取消时遵循这些规则：

1. 用 `try/finally` 释放资源。
2. `CancelledError` 直接继承 `BaseException`；普通的 `except Exception` 不会捕获它。
3. 若显式捕获 `CancelledError`，通常应在清理后重新抛出。
4. 取消是请求，不意味着远端服务器已经撤销操作，也不意味着已经提交的数据库写入会回滚。
5. 不要通过捕获 `BaseException`、空的 `except` 或无限重试让任务拒绝结束。

异常继承关系见 [asyncio 异常](https://docs.python.org/3.14/library/asyncio-exceptions.html)。

### 7.6 同步 I/O 如何接入异步代码

在事件循环线程内调用 `time.sleep()` 或阻塞式文件、HTTP API，会暂停该线程上其他任务的推进。已有同步 I/O 可以交给线程执行：

```python
import asyncio
from pathlib import Path
from tempfile import TemporaryDirectory


async def main() -> None:
    with TemporaryDirectory() as directory:
        path = Path(directory) / "message.txt"
        await asyncio.to_thread(path.write_text, "hello", encoding="utf-8")
        content = await asyncio.to_thread(path.read_text, encoding="utf-8")
        assert content == "hello"


if __name__ == "__main__":
    asyncio.run(main())
```

这里的目的在于将同步文件操作移出事件循环线程，不是宣称小文件读取一定会更快。普通 GIL 构建中，不应默认用 `to_thread()` 加速纯 Python CPU 大循环；取消等待通常也不会停止已经运行的线程函数。[在线程中运行](https://docs.python.org/3.14/library/asyncio-task.html#running-in-threads)

### 7.7 在 Web 服务里迁移这些经验

- 框架已经管理事件循环时，在异步处理函数中 `await` 工作，不自己调用 `asyncio.run()`。
- `async def` 处理函数里调用同步数据库或 HTTP 接口，仍可能阻塞事件循环；选择异步驱动或明确安排线程执行。
- 客户端连接池与并发额度通常需要应用级生命周期，不能每次请求无限创建连接。
- 本文每次 `main()` 新建的信号量，只限制该次运行。多个请求、worker 进程或服务副本各有一份时，总并发会叠加。
- 内存中的 Task 不是持久任务队列；进程退出、请求取消或部署重启时，业务是否允许工作丢失，需要另外设计。

这些是进入阶段四前应具备的判断能力，不要求现在实现一套 Web 服务。

### 7.8 异步验证与调试：让失败稳定地暴露

调试异步程序时，先开启诊断信息，再判断是没有启动、没有等待、没有处理异常，还是阻塞了事件循环。

```bash
PYTHONASYNCIODEBUG=1 python -W default example.py
```

这条命令适用于本文使用的 macOS / Linux shell，也可以直接在代码入口使用 `asyncio.run(main(), debug=True)`。常见信号及排查方向如下：

| 信号 | 常见原因 | 处理方向 |
| --- | --- | --- |
| `coroutine ... was never awaited` | 创建协程后没有等待或调度 | 找到创建位置，明确由谁负责执行 |
| `Task exception was never retrieved` | Task 失败，但没有调用方读取异常 | 优先纳入 TaskGroup，或明确等待并处理结果 |
| 慢回调日志 | 某段同步代码长时间占用事件循环线程 | 检查阻塞 I/O、CPU 计算和同步日志输出 |
| `ResourceWarning` | 文件、连接等资源没有及时关闭 | 检查上下文管理器和异常退出路径 |

Debug 模式能帮助发现问题，不是完整的正确性证明。日志中的慢回调也不等于慢网络请求：正常异步等待期间，事件循环仍可以处理其他任务。[asyncio 开发与调试](https://docs.python.org/3.14/library/asyncio-dev.html)

**验证取消时，应等待任务真的进入目标状态，而不是睡一个猜测的时长。**

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()
    baseline = asyncio.all_tasks()

    async def job() -> None:
        try:
            started.set()
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    task = asyncio.create_task(job(), name="cancellation-demo")
    try:
        async with asyncio.timeout(2):
            await started.wait()
    finally:
        task.cancel()
        try:
            await task
        except asyncio.CancelledError:
            pass

    assert task.cancelled()
    assert cleaned.is_set()
    assert asyncio.all_tasks() == baseline


if __name__ == "__main__":
    asyncio.run(main(), debug=True)
```

事件保证任务已经开始；两秒超时只是避免验证挂死，不承担任务之间的同步职责。调用方在等待已经取消的任务时处理 `CancelledError`，与业务协程吞掉取消并继续工作，是不同情况。

**隔离外部 I/O 时，检查“被等待过”，不能只检查“被调用过”。** 标准库 `AsyncMock` 可以模拟异步结果与失败，无需连接真实服务：

```python
import asyncio
from collections.abc import Awaitable, Callable
from unittest.mock import AsyncMock


async def retry_once(load: Callable[[], Awaitable[str]]) -> str:
    try:
        return await load()
    except TimeoutError:
        return await load()


async def main() -> None:
    remote = AsyncMock(side_effect=[TimeoutError("模拟超时"), "ready"])
    assert await retry_once(remote) == "ready"
    assert remote.await_count == 2
    remote.assert_awaited_with()

    broken = AsyncMock(side_effect=ValueError("输入错误"))
    try:
        await retry_once(broken)
    except ValueError:
        pass
    else:
        raise AssertionError("非超时错误应传播")
    broken.assert_awaited_once_with()

    cancelled = AsyncMock(side_effect=asyncio.CancelledError())
    try:
        await retry_once(cancelled)
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("取消应传播")
    cancelled.assert_awaited_once_with()


if __name__ == "__main__":
    asyncio.run(main())
```

`retry_once` 是用于验证行为的最小函数，只对一次超时重试；真实重试策略还需考虑幂等性、总时间预算和退避。Mock 证明的是调用方控制流，真实连接是否被正确关闭仍需要相应集成验证。[AsyncMock](https://docs.python.org/3.14/library/unittest.mock.html#unittest.mock.AsyncMock)

### 7.9 `ContextVar`：传递请求上下文而不混淆任务

日志中的请求 ID 经常需要跨越多层函数。一直显式传参是清楚且有效的选择；当上下文属于横跨调用链的日志、追踪信息时，可以使用 `ContextVar`。

普通模块全局变量只有一份；`threading.local()` 按线程区分，而一个事件循环线程可以同时承载多个请求任务。`ContextVar` 可以让这些任务拥有各自的上下文绑定，适合表达请求 ID 等信息。

```python
import asyncio
from contextvars import ContextVar

request_id: ContextVar[str] = ContextVar("request_id", default="-")


async def read_request() -> str:
    await asyncio.sleep(0)
    return request_id.get()


async def handle(identifier: str) -> str:
    token = request_id.set(identifier)
    try:
        return await read_request()
    finally:
        request_id.reset(token)


async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(handle("request-a"))
        second = group.create_task(handle("request-b"))
    assert first.result() == "request-a"
    assert second.result() == "request-b"
    assert request_id.get() == "-"

    token = request_id.set("parent-before")
    try:
        async with asyncio.TaskGroup() as group:
            child = group.create_task(read_request())
            request_id.set("parent-after")
        assert child.result() == "parent-before"
        assert request_id.get() == "parent-after"
        assert await asyncio.to_thread(request_id.get) == "parent-after"
    finally:
        request_id.reset(token)
    assert request_id.get() == "-"


if __name__ == "__main__":
    asyncio.run(main())
```

这里观察到两个层次：独立任务的绑定彼此隔离；默认创建子 Task 时，它继承创建时的上下文，父任务之后改自己的绑定不会自动同步给子任务。`asyncio.to_thread()` 也会把执行该操作时的上下文带到工作线程，但不能把这个结论推广为所有线程或进程接口。

实践中还要注意：

- 在模块顶层创建 `ContextVar`，在进入请求时 `set()`，退出时用相应 token 恢复原绑定。
- 使用 `try/finally` 调用 `reset()`，避免异常或取消绕过恢复；这里保持 Python 3.11+ 可用写法。
- 上下文复制不是对值做深拷贝。若值是一份可变字典，不同上下文可能仍引用同一个字典；优先使用字符串等不可变值，或显式创建独立容器。
- `ContextVar` 不提供锁、共享缓存或进程间通信，也不能替代业务参数与权限校验。

可以将本例的请求 ID 加到第 9 节的日志中，但不要把 token 或敏感业务对象直接写入日志。[ContextVar 与 asyncio 支持](https://docs.python.org/3.14/library/contextvars.html#asyncio-support)

## 8. 多进程：把计算交给多个 CPU 核心

### 8.1 从任务边界理解 `multiprocessing`

每个进程有自己的解释器和地址空间，因此普通 GIL 构建下，不同进程也能同时执行 Python 计算。代价是数据通常要序列化后传递，不能像同一线程内那样直接共享所有对象。

常见接口关系：

| 接口 | 关注点 |
| --- | --- |
| `multiprocessing.Process` | 手动管理一个子进程及其启动、结束 |
| `multiprocessing.Queue` / `Pipe` | 显式在进程间传递数据 |
| `multiprocessing.Pool` | 管理可复用的计算进程池 |
| `ProcessPoolExecutor` | 使用 `submit()` / `map()` 提交任务，接口与线程池接近 |

对于“输入一组值，独立计算，再汇总”的任务，先学习进程池更容易看清任务划分。`ProcessPoolExecutor` 底层使用 `multiprocessing`，并非另一种绕开进程规则的机制。[进程池说明](https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor)

### 8.2 可直接运行的 CPU 计算示例

保存为 `process_demo.py`，从终端运行。此处选择纯 Python 计算以突出执行模型；实际工作中，应先评估是否有更好的算法或原生库实现。

```python
import multiprocessing
from concurrent.futures import ProcessPoolExecutor
from time import perf_counter


def sum_squares(limit: int) -> int:
    return sum(number * number for number in range(limit))


def main() -> None:
    inputs = [200_000, 250_000, 300_000, 350_000]

    started = perf_counter()
    serial = [sum_squares(limit) for limit in inputs]
    serial_seconds = perf_counter() - started

    context = multiprocessing.get_context("spawn")
    started = perf_counter()
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        parallel = list(pool.map(sum_squares, inputs))
    parallel_seconds = perf_counter() - started

    expected = [limit * (limit - 1) * (2 * limit - 1) // 6 for limit in inputs]
    assert serial == parallel == expected
    print(f"串行：{serial_seconds:.4f}s")
    print(f"进程池：{parallel_seconds:.4f}s")


if __name__ == "__main__":
    main()
```

```bash
python process_demo.py
```

这里故意使用较小输入，便于快速验证；进程池很可能更慢，因为计时包含启动与退出。需要比较吞吐时，再增大每项工作量、复用同一个进程池并进行多次测量。示例末尾的求和公式也提醒我们：算法改进往往比调度方式更有价值。

### 8.3 为什么要顶层函数、主入口保护和可序列化数据

- `sum_squares` 定义在模块顶层，子进程可通过模块找到它。
- `if __name__ == "__main__":` 防止子进程导入模块时再次创建进程池。
- 参数和返回值应能被 pickle 序列化；不要直接传入数据库连接、打开的文件或带复杂运行状态的对象。
- `lambda`、局部函数和交互式环境中的函数不适合作为这里的进程池任务。
- 普通全局列表并不自动共享。子进程修改自己的列表，不会使父进程列表同步变化。
- 任务异常需要通过读取结果暴露；使用 `map()` 时，异常可能在消费结果迭代器时抛出。

序列化限制和主模块可导入要求见 [ProcessPoolExecutor 文档](https://docs.python.org/3.14/library/concurrent.futures.html#processpoolexecutor)。

### 8.4 不依赖操作系统默认启动方式

本例显式使用 `spawn`：启动新的解释器，再导入所需模块。这样可以直接练习跨平台必须面对的模块导入与数据传递约束。

| 启动方式 | 大致行为 | 学习时关注什么 |
| --- | --- | --- |
| `spawn` | 启动新解释器 | 导入安全、主入口保护、参数可序列化 |
| `fork` | 从父进程复制进程状态 | 多线程父进程与继承资源会带来复杂问题 |
| `forkserver` | 由独立服务进程负责派生子进程 | 可用性与默认选择受平台和 Python 版本影响 |

Windows、macOS 默认采用 `spawn`。Python 3.14 在支持条件满足的 POSIX 平台（如 Linux）将默认改为 `forkserver`，`fork` 不再是任何平台的默认方式。不要照搬旧文章中“Linux 一定默认 fork”的假设。[启动方式与版本变更](https://docs.python.org/3.14/library/multiprocessing.html#contexts-and-start-methods)

### 8.5 多进程也要有容量边界

增加进程数不会无限提升速度。要一起评估：

1. **每项工作大小：** 极小任务常被调度成本淹没，可先合理分批。
2. **传输体积：** 大对象在进程间反复复制，可能比计算更贵。
3. **任务积压：** 不要向执行器一次提交无限任务；本文仅提交固定的四项输入。大输入要限制在途任务；Python 3.14 的 `Executor.map()` 还提供 `buffersize`，但这不属于本文 3.11+ 通用示例。
4. **内存与 CPU 配额：** 容器可用核心、服务已有 worker 数和每个进程的内存都影响上限。
5. **退出语义：** 取消 Future 通常不能停止已经开始的计算，离开执行器上下文默认会等待工作结束。

在异步服务中调用进程池，可以使用事件循环的 `run_in_executor(pool, func, ...)` 等接口等待结果；同时要在应用生命周期内复用并关闭池，不要为每个请求创建一个新池。

### 8.6 先测瓶颈，再解释优化结果

计时、性能剖析和内存追踪解决的是不同问题：

| 工具 | 要回答的问题 | 阅读结果时的边界 |
| --- | --- | --- |
| `perf_counter()` | 一段操作经过了多久 | 等待时间、进程启动等都会计入所包围的区间 |
| `timeit` | 一个短小操作反复执行的耗时如何 | 适合微基准，不直接代表完整服务；默认会临时关闭垃圾回收 |
| `cProfile` | 哪些函数被频繁调用、主要成本在哪里 | 剖析本身有开销；父进程的剖析不会自动覆盖子进程计算 |
| `tracemalloc` | 哪些 Python 分配仍存活、峰值多高 | 不能简单等同于进程整体内存 |

下面用同一个计算目标比较两种实现，并查看函数调用统计：

```python
import cProfile
import io
import pstats
from timeit import repeat

LIMIT = 20_000


def loop_sum() -> int:
    return sum(number * number for number in range(LIMIT))


def formula_sum() -> int:
    return LIMIT * (LIMIT - 1) * (2 * LIMIT - 1) // 6


assert loop_sum() == formula_sum()
for work in (loop_sum, formula_sum):
    samples = repeat(work, number=10, repeat=5)
    print(work.__name__, [round(seconds / 10, 8) for seconds in samples])

profiler = cProfile.Profile()
profiler.runcall(loop_sum)
output = io.StringIO()
pstats.Stats(profiler, stream=output).strip_dirs().sort_stats("cumulative").print_stats(5)
print(output.getvalue())
```

每个打印的时间是对应批次的单次平均耗时；多次重复可以观察环境噪声，不应只挑一次有利结果。`cumulative` 关注函数及其子调用的累计时间，`tottime` 关注函数自身耗时；调用关系有重叠时，不要把所有累计时间简单相加。

这里先用断言保证两种算法结果一致，再观察成本差异。比较串行、线程池与进程池时，也应保持输入和工作定义一致，分别说明是否包含启动、序列化与结果汇总。不要把公式算法的收益误归因于并发方式。[timeit](https://docs.python.org/3.14/library/timeit.html) 与 [Python 性能剖析器](https://docs.python.org/3.14/library/profile.html)

## 9. 综合实战：有界异步任务流水线

### 9.1 场景与验收标准

实现一个本地模拟的数据补全任务：生成 12 个任务，使用固定数量的 worker 模拟外部查询；其中一个任务超时，其余成功，最后生成摘要。

所有 I/O 都通过 `asyncio` 模拟，不需要 API Key、网络或第三方依赖。这个练习把四个主题放到一条实际数据路径里：

```text
生成器逐个创建 Job
        ↓
有界 Queue：满了就等待，限制排队数量
        ↓
固定 worker：执行带超时的异步操作
        ↓
Report：只保存计数，不收集全部结果
        ↓
__call__ 读取摘要，__str__ 展示摘要

外层装饰器记录总耗时，TaskGroup 管理 worker 生命周期
```

成功标准：

- 成功 11 项、超时 1 项，总数为 12。
- 同时执行的模拟请求不超过 3 个。
- 队列最多积压 6 项，不为每条输入创建独立 Task。
- 超时作为预期业务结果被统计；其他意外异常向外传播。
- 正常结束时，worker 已退出，正在执行的请求数归零。

### 9.2 完整示例

保存为 `stage3_pipeline.py`：

```python
import asyncio
from collections.abc import Awaitable, Callable, Iterator
from dataclasses import dataclass
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")


def measured(
    func: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(func)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            print(f"总耗时：{perf_counter() - started:.4f}s")

    return wrapper


@dataclass(frozen=True)
class Job:
    item_id: int


@dataclass
class Report:
    succeeded: int = 0
    timed_out: int = 0
    active: int = 0
    peak: int = 0

    def __call__(self) -> dict[str, int]:
        return {"succeeded": self.succeeded, "timed_out": self.timed_out}

    def __str__(self) -> str:
        return (
            f"成功={self.succeeded}，超时={self.timed_out}，"
            f"峰值并发={self.peak}"
        )


def iter_jobs(total: int) -> Iterator[Job]:
    for item_id in range(total):
        yield Job(item_id)


async def enrich(job: Job) -> int:
    if job.item_id == 7:
        await asyncio.Event().wait()  # 确定性地等待，直到外部超时取消。
    await asyncio.sleep(0.01)
    return job.item_id * 10


async def worker(queue: asyncio.Queue[Job | None], report: Report) -> None:
    while True:
        job = await queue.get()
        try:
            if job is None:
                return

            report.active += 1
            report.peak = max(report.peak, report.active)
            try:
                async with asyncio.timeout(0.2):
                    result = await enrich(job)
                assert result == job.item_id * 10
                report.succeeded += 1
            except TimeoutError:
                report.timed_out += 1
            finally:
                report.active -= 1
        finally:
            queue.task_done()


@measured
async def run_pipeline() -> Report:
    worker_count = 3
    queue: asyncio.Queue[Job | None] = asyncio.Queue(maxsize=6)
    report = Report()

    async with asyncio.TaskGroup() as group:
        for _ in range(worker_count):
            group.create_task(worker(queue, report))

        for job in iter_jobs(12):
            await queue.put(job)

        for _ in range(worker_count):
            await queue.put(None)

        await queue.join()

    assert report() == {"succeeded": 11, "timed_out": 1}
    assert report.active == 0
    assert 1 <= report.peak <= worker_count
    assert queue.empty()
    return report


if __name__ == "__main__":
    print(asyncio.run(run_pipeline()))
```

```bash
python stage3_pipeline.py
```

输出包含一行耗时和一行摘要；普通运行中会观察到峰值并发为 3。断言检查的是业务结果和并发边界，不绑定具体耗时。

### 9.3 逐步理解这个设计

1. **生产者不预先构造完整列表。** `iter_jobs()` 每次产出一个任务；`queue.put()` 在队列满时等待。
2. **只创建固定数量的 worker。** Task 数量不会随输入条数增长；队列之外还会有 worker 正在处理的任务，以及生产者当前等待入队的一项。
3. **终止信号是 `None`。** 队列中的真实任务都是 `Job`，不会与信号混淆。每个 worker 消费一个终止信号后退出。
4. **每次 `get()` 配对一次 `task_done()`。** 包括终止信号，否则 `join()` 可能永远等不到未完成计数归零。
5. **业务失败与程序错误分开。** 超时计入报表；断言错误或其他未预期异常会触发 `TaskGroup` 的失败收尾。
6. **共享计数更新之间没有 `await`。** 在本例单事件循环线程内，这些短更新不会因协程调度彼此穿插；这个条件不能推广为多线程安全保证。
7. **资源生命周期可见。** 离开 `TaskGroup` 时所有 worker 已结束；装饰器在 `finally` 中记录正常或异常退出的耗时。

`queue.join()` 表示队列里的工作已按约定调用 `task_done()`，并不单独保证每个 worker 已退出；这里由外层 `TaskGroup` 补上这个保证。[队列完成计数](https://docs.python.org/3.14/library/asyncio-queue.html#asyncio.Queue.join)

队列容量限制的是项目数量，不是字节总量；如果单个 `Job` 携带巨大数据，仍需额外评估内存。示例不持久化任务、不调用真实接口，也不包含重试策略，这些都留给具体业务约束决定。

### 9.4 自己动手的四个改造练习

| 练习 | 修改内容 | 必须观察到的结果 |
| --- | --- | --- |
| 调整并发 | 分别使用 1、3、5 个 worker | 结果计数不变，峰值不超过 worker 数；耗时受唯一超时任务影响 |
| 放大输入 | 增加任务数，同时更新预期计数 | Task 数仍固定；报表只存计数，队列不无限增长 |
| 制造程序错误 | 让 `enrich()` 对某个非 7 的编号抛出 `ValueError` | 调用方收到异常组，其他任务被取消，运行不会一直等待 `queue.join()` |
| 外部取消 | 把 `run_pipeline()` 放入 Task，启动后请求取消并等待它 | `CancelledError` 向调用方传播，`finally` 被执行，没有遗留 worker |

先完成现有语义的验证，再把 `enrich()` 替换成实际异步 HTTP 操作。不要一开始同时加入数据库、重试、分布式队列和 Web 接口，否则很难判断错误来自哪一层。

### 10.1 作用域与共享对象：独立的日志收集器

**题目：** 为 `build`、`test`、`deploy` 创建三个回调。每个回调接收一条消息，返回自己的标签和历史消息。再次创建同标签收集器时，历史应为空；调用方拿到的历史不能直接修改收集器内部列表。

**验收：** 标签分别正确，三个收集器互不污染，两次创建同标签收集器也不共享状态。

<details>
<summary>参考答案与解释</summary>

```python
from collections.abc import Callable


def make_collector(label: str) -> Callable[[str], tuple[str, tuple[str, ...]]]:
    history: list[str] = []

    def collect(message: str) -> tuple[str, tuple[str, ...]]:
        history.append(message)
        return label, tuple(history)

    return collect


build, test, deploy = [
    make_collector(label) for label in ("build", "test", "deploy")
]
assert build("started") == ("build", ("started",))
assert test("passed") == ("test", ("passed",))
assert deploy("ready") == ("deploy", ("ready",))
assert build("finished") == ("build", ("started", "finished"))
assert make_collector("build")("new") == ("build", ("new",))
```

### 10.2 方法与属性：可继承的 worker 配置

**题目：** 实现一个 `PoolConfig`，允许从字符串创建对象，只允许正整数 worker 数；把实例的展示方法保存成独立变量后仍能调用。子类调用构造入口应得到子类实例。

**验收：** 创建和后续赋值都经过校验，非法赋值不破坏旧值，方法绑定和子类构造正确。

<details>
<summary>参考答案与解释</summary>

```python
class PoolConfig:
    def __init__(self, workers: int) -> None:
        self.workers = workers

    @classmethod
    def from_text(cls, text: str) -> "PoolConfig":
        return cls(int(text))

    @property
    def workers(self) -> int:
        return self._workers

    @workers.setter
    def workers(self, value: int) -> None:
        if type(value) is not int or value <= 0:
            raise ValueError("workers 必须是正整数")
        self._workers = value

    def describe(self) -> str:
        return f"workers={self.workers}"


class LocalPoolConfig(PoolConfig):
    pass


config = LocalPoolConfig.from_text("3")
assert isinstance(config, LocalPoolConfig)
describe = config.describe
assert describe() == "workers=3"
try:
    config.workers = 0
except ValueError:
    pass
else:
    raise AssertionError("应拒绝零个 worker")
assert config.workers == 3
```

题目明确只接受整数，因此这里用运行时检查，并排除 `bool`；Python 的 `bool` 是 `int` 的子类，仅用 `isinstance(value, int)` 会接纳布尔值。`cls(...)` 保留子类构造能力，`config.describe` 保存实例绑定。如果多个类需要复用同样的字段校验规则，可以参考第 3.7 节的描述符，但规则只出现一次时无需额外抽象。

</details>

### 10.3 数据模型：稳定且按租户隔离的缓存键

**题目：** 用数据类实现缓存键，包含租户和权限集合。权限顺序不同、存在重复项时应得到相同键；不同租户必须得到不同键。修改调用方最初传入的列表，不能改变已有键。

**验收：** 相等键在集合中去重，字典能用等价键读取结果，外部列表修改不影响缓存键。

<details>
<summary>参考答案与解释</summary>

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class AccessKey:
    tenant: str
    permissions: tuple[str, ...]

    @classmethod
    def from_permissions(cls, tenant: str, values: list[str]) -> "AccessKey":
        return cls(tenant, tuple(sorted(set(values))))


permissions = ["write", "read", "read"]
first = AccessKey.from_permissions("team-a", permissions)
same = AccessKey.from_permissions("team-a", ["read", "write"])
other = AccessKey.from_permissions("team-b", ["read", "write"])
permissions.append("admin")

assert first == same
assert hash(first) == hash(same)
assert first != other
assert len({first, same, other}) == 2
assert first.permissions == ("read", "write")
cache = {first: "allowed"}
assert cache[same] == "allowed"
```

题目把权限定义为集合，所以去重和排序是有意的业务规范化；如果顺序具有含义，就不能这样处理。元组中的字符串不可变，适合参与哈希。不同对象也可能产生哈希碰撞，因此验收不应要求 `hash(first) != hash(other)`。本题只验证缓存键结构，真实授权缓存仍要处理权限变更、失效和授权来源。

</details>

### 10.4 异步验证：成功、失败、取消都可观察

**题目：** 给异步服务调用编写离线验证：成功时返回结果，业务异常向调用方传播，取消时远端模拟器执行清理，而且没有遗留任务。不连接真实网络，不靠固定睡眠猜测启动时机。

**验收：** 使用 `AsyncMock` 检查实际等待参数；用事件证明任务开始与清理，完成后任务集合恢复。

<details>
<summary>参考答案与解释</summary>

```python
import asyncio
from collections.abc import Awaitable, Callable
from unittest.mock import AsyncMock


async def load_job(
    job_id: str, remote: Callable[[str], Awaitable[str]]
) -> str:
    return await remote(job_id)


async def main() -> None:
    baseline = asyncio.all_tasks()
    success = AsyncMock(return_value="ready")
    assert await load_job("job-1", success) == "ready"
    success.assert_awaited_once_with("job-1")

    failure = AsyncMock(side_effect=ValueError("bad job"))
    try:
        await load_job("job-2", failure)
    except ValueError:
        pass
    else:
        raise AssertionError("业务异常应传播")
    failure.assert_awaited_once_with("job-2")

    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def blocked(job_id: str) -> str:
        try:
            started.set()
            await asyncio.Event().wait()
            return job_id
        finally:
            cleaned.set()

    remote = AsyncMock(side_effect=blocked)
    task = asyncio.create_task(load_job("job-3", remote))
    try:
        async with asyncio.timeout(2):
            await started.wait()
    finally:
        task.cancel()
        try:
            await task
        except asyncio.CancelledError:
            pass

    remote.assert_awaited_once_with("job-3")
    assert task.cancelled()
    assert cleaned.is_set()
    assert asyncio.all_tasks() == baseline


if __name__ == "__main__":
    asyncio.run(main(), debug=True)
```

`assert_awaited_once_with()` 同时检查等待次数与参数；单纯检查 `called` 无法区分“创建了协程”和“实际等待了它”。`blocked` 的返回语句正常不会到达，取消会经过 `finally`；如果把业务代码改成吞掉取消，状态断言就会暴露问题。超时专项验证可结合第 7.5 节的独立示例完成。

</details>

### 10.5 上下文隔离：可变值不自动深拷贝

**题目：** 父任务保存一份包含请求 ID 的上下文字典。创建两个子任务，各自更新请求 ID 并读取，父任务的字典必须保持不变。解释为什么直接修改 `ContextVar.get()` 返回的字典会出问题。

**验收：** 两个子任务分别读到自己的 ID，父字典不变，退出上下文后恢复未绑定状态。

<details>
<summary>参考答案与解释</summary>

```python
import asyncio
from contextvars import ContextVar

metadata: ContextVar[dict[str, str]] = ContextVar("metadata")


async def child(identifier: str) -> str:
    local = {**metadata.get(), "request_id": identifier}
    token = metadata.set(local)
    try:
        await asyncio.sleep(0)
        return metadata.get()["request_id"]
    finally:
        metadata.reset(token)


async def main() -> None:
    parent = {"request_id": "parent"}
    token = metadata.set(parent)
    try:
        async with asyncio.TaskGroup() as group:
            first = group.create_task(child("a"))
            second = group.create_task(child("b"))
        assert first.result() == "a"
        assert second.result() == "b"
        assert metadata.get() is parent
        assert parent == {"request_id": "parent"}
    finally:
        metadata.reset(token)
    assert metadata.get(None) is None


if __name__ == "__main__":
    asyncio.run(main())
```

子任务最初继承的是指向同一个字典的绑定。直接写 `metadata.get()["request_id"] = ...` 会修改共享对象；答案先新建字典再设置当前上下文。这里的值都是字符串，因此浅拷贝足够；嵌套可变值仍需明确所有权。

</details>

### 10.6 内存诊断：找到仍存活的分配

**题目：** 创建一批记录并保留引用，使用快照比较定位分配位置，再查看当前追踪量和峰值。解释为什么函数返回后只看当前占用，可能漏掉处理过程中的大内存峰值。

**验收：** 能打印按行汇总的正向分配变化，理解字节数是环境相关的观测，不写死内存阈值。

<details>
<summary>参考答案与解释</summary>

```python
import tracemalloc


def make_records(count: int) -> list[dict[str, int]]:
    return [{"item_id": index} for index in range(count)]


tracemalloc.start()
try:
    before = tracemalloc.take_snapshot()
    records = make_records(10_000)
    after = tracemalloc.take_snapshot()
    assert len(records) == 10_000
    assert records[-1] == {"item_id": 9_999}

    growth = [
        change
        for change in after.compare_to(before, "lineno")
        if change.size_diff > 0
    ]
    for change in growth[:3]:
        print(change)

    current, peak = tracemalloc.get_traced_memory()
    print(f"当前追踪量：{current / 1024:.1f} KiB")
    print(f"追踪峰值：{peak / 1024:.1f} KiB")
    assert peak >= current
finally:
    tracemalloc.stop()
```

快照拍摄时 `records` 仍被引用，因此可以定位这批存活分配。若先释放中间结果再拍照，快照不会保留它们过去占用的全部内存；峰值计数则可以帮助识别这种短暂高峰。诊断代码和快照操作自身也会产生分配，输出中出现工具内部记录不代表全部内存都来自业务代码。

继续练习：把第 5.6 节的两种求和实现与第 8.6 节的测量方式结合，分别记录结果、耗时和内存，写出“观测事实”和“解释假设”，不要仅写“生成器更快更省内存”。

</details>

## 12. 常见误区与阶段验收

### 12.1 前端开发最容易迁移错误的直觉

| 容易出现的判断 | 应改为检查什么 |
| --- | --- |
| 写了 `async def` 就不会阻塞 | 函数体里是否仍有同步 I/O 或长时间 CPU 计算 |
| 调用了协程函数，任务就启动了 | 协程是否被 `await` 或包装成 Task |
| 顺序写多个 `await` 就是在并发 | 独立任务是否先被调度，再统一等待 |
| `gather()` 有任务失败，会自动取消全部兄弟任务 | 分清首次异常传播、外层取消与 TaskGroup 的差异 |
| 信号量设为 10，就最多只占 10 个任务的内存 | 是否预创建了大量 Task，队列和结果是否有界 |
| 超时意味着远端操作已撤销 | 本地等待、运行线程、远端请求各自是否支持取消 |
| 有 GIL 就不需要锁 | 一整个业务读改写流程是否会交错 |
| 多进程就是随便把函数丢进去 | 函数能否导入，数据能否序列化，进程如何关闭 |
| `yield` 自动带来低内存 | 下游是否又转成列表或累积全部结果 |
| 使用装饰器后函数契约自然不变 | 参数、返回值、异常、元数据和异步等待是否保留 |
| Python 新版本已经默认没有 GIL | 具体解释器构建、运行配置与依赖是否支持 |
| 吞掉错误、记录日志就算可靠 | 调用方能否感知失败，是否产生错误的成功结果 |
| 缩进形成了与 JS `let` 一样的块级作用域 | 普通 `if`、`for` 不创建独立局部作用域；区分定义与名称绑定 |
| 每次调用都会新建默认参数中的列表 | 默认值是在函数定义执行时求值，是否应使用 `None` 哨兵 |
| `frozen=True` 就是深度不可变 | 字段指向的对象是否仍可修改，参与哈希的字段是否可哈希 |
| 复制了 Context，就不会共享任何对象 | 复制的是上下文绑定，值中的可变对象可能仍然共享 |
| Mock 被调用过就代表异步操作执行过 | 是否检查了 await 次数、参数与异常传播 |
| 当前内存很小，说明没有出现内存高峰 | 是否分别观察当前值、峰值与仍存活的快照分配 |

### 12.2 自测问题与答案要点

先遮住答案，尝试用自己的话解释：

| 问题 | 答案要点 |
| --- | --- |
| 为什么 `list(generator)` 第二次变成空列表？ | 原生成器是带消费位置的迭代器，第一次已经耗尽；需要重新创建 |
| `wraps` 与 `ParamSpec` 是否可以互相替代？ | 不可以；前者处理运行时元数据，后者表达静态参数关系 |
| 调用 `async_fn()` 后没有输出，是事件循环坏了吗？ | 先检查是否只是创建了协程对象，没有等待或调度 |
| 同步装饰器直接调用异步函数，计时为什么很短？ | 它可能只测到了协程对象创建时间，没有等待异步工作 |
| `TaskGroup` 里一个普通异常会怎样？ | 请求取消其他任务，等待清理，再传播异常组；特殊异常另有规则 |
| 只有一个事件循环线程，为什么还会丢失更新？ | 共享状态的读取与写入之间发生挂起，允许其他任务介入 |
| 使用 `Queue(maxsize=6)` 就完全不需要关注内存了吗？ | 它只限制排队项目数，还要算单项体积、在途任务与结果积累 |
| 多进程返回结果正确但更慢，是否实现一定错误？ | 不一定；启动、序列化、通信成本可能大于并行收益 |
| 为什么多进程代码在交互式控制台可能失败？ | 子进程需要可导入的主模块与任务函数，交互式定义不满足同样条件 |
| `__getattr__` 对缺失属性返回 `None` 有什么风险？ | `hasattr()` 可能误判属性存在，调用方失去正确的失败信号 |
| 为什么循环中保存的回调都返回最后一个编号？ | 回调调用时读取同一外层变量；工厂闭包或默认参数可以保存各自的值 |
| 为什么 `callback = obj.method` 后仍能访问原实例？ | 取到的是持有实例的绑定方法，和 JS 普通方法脱离接收者的行为不同 |
| `classmethod` 构造对象时为什么用 `cls`？ | 让子类调用时仍创建对应子类，而不是写死基类 |
| 数据类冻结后为什么仍可能不可哈希？ | 自动生成哈希不意味着所有字段都能哈希，列表字段仍会导致错误 |
| 为什么子任务改 ContextVar 不影响父任务，但改里面的字典可能影响？ | 重新绑定与修改同一个共享对象是不同操作 |
| 为什么不把测到的加速倍数写成断言？ | 硬件、负载、构建与测量开销都会影响时间；应断言结果并报告测量条件 |
